## 결론부터

> **서비스 유형이 바뀌면 제품 요구사항 정의서(Product Requirements Document, PRD)의 세 섹션(규제 체크·성공 지표·AI 활용점)과 프롬프트의 세 칸([자료]·[형식]·[검증])이 바뀌고, 나머지는 같다.**

- **같은 것**: 요청 6요소 틀(역할·목적·독자·자료·형식·검증), PRD 8섹션 뼈대, 두괄식·표 양식·지표 3종, 3관점 리뷰(리더십·디자이너·엔지니어링 매니저(Engineering Manager, EM)), 별도 대화 검수, `[가정]`·`[확인 필요]` 표기, 문서 계층(2-Pager → PRD → Spec/HLD → ADR → Ops). 오늘 강의가 머니핏 하나로 하루를 관통해도 다른 유형에 옮겨 쓸 수 있는 이유가 이것이다.
- **바뀌는 것**: 핀테크 7유형(지급결제·송금 / 여수신·대출 / 자산관리·마이데이터 / 투자·증권 / 보험 / 인증·보안·이상거래탐지시스템(Fraud Detection System, FDS)·자금세탁방지(Anti-Money Laundering, AML) / 기업 간 거래(Business-to-Business, B2B)·임베디드 금융·서비스형 뱅킹(Banking as a Service, BaaS))마다 사용자 여정, 지표 3종의 이름과 측정 이벤트, 컴플라이언스에 물어볼 질문, 환각이 가장 위험한 자리가 다르다. 그 차이는 프롬프트에서 **[자료]에 무엇을 붙이나 · [형식]에 어떤 표를 요구하나 · [검증]에서 무엇을 금지하나** 세 칸으로만 나타난다(§2).
- **문서 관리는 유형과 무관하게 같은 다섯 원칙**으로 안정시킨다 — PRD가 단일 진실 원천(Single Source of Truth, SSOT), 메타 헤더·Change Log, 버전(v0.1 초안 → v1.0 승인), 3관점 평가 게이트, 규제 섹션은 "질문 목록 + 회신 기록"으로 누적. 유형별로 PRD에 **반드시 추가되는 섹션은 1개씩**만이다(§3).
- **프롬프트 기법은 6단 사다리**(L1 6요소 카드 → L2 재요청·검증 루프 → L3 역할 분리 → L4 템플릿·프로젝트화 → L5 컨텍스트 파일 → L6 하네스)로 올라간다. 오늘 실습은 L1~L3(무료 웹 계정·복사·붙여넣기), L4~L6은 강사 시연 + 가져가기 플레이북. 어느 유형이든 **다음 레벨로 가는 신호는 "같은 것을 반복하고 있다"는 느낌**이다(§4).
- 이 문서의 산출물: 유형별 렌즈표 7개(§2) · 문서 관리 원칙 + 유형별 추가 섹션(§3) · 사다리 L1~L6(§4) · 적용 예시 3개(§5, 가상) · **오늘 강의 삽입 장표 후보 10장**(§6 — 본편 추가 4 · 부록/Optional 6, 채택 여부는 `00-review-checklist` 결정 항목으로 올린다).

## 1. 렌즈의 원리 — 바뀌는 3+3, 같은 것

| 구분 | 항목 | 유형이 바뀌면 | 왜 이렇게 나누나 |
|------|------|-------------|----------------|
| **바뀐다** (PRD) | §6 성공 지표 | 지표 이름·분모·측정 이벤트가 바뀐다(예: 목표 설정율 → 결제 성공률 → 청구 접수 완료율) | 지표는 여정에서 나오고, 여정은 유형마다 다르다 |
| | §7 규제·리스크 체크 | 관련 법·감독기관·질문 목록이 바뀐다 | 같은 "자동이체"라도 결제 서비스와 자산관리 서비스에서 물어볼 질문이 다르다 |
| | §4 솔루션과 AI 활용점 | AI가 가치를 만드는 자리와 **금지되는 자리**가 바뀐다 | 대출·보험·FDS에서는 AI가 "판단"하면 안 되는 자리가 명확히 있다 |
| **바뀐다** (프롬프트) | [자료] | 무엇을 붙이나 — 5개 핵심 입력 외에 약관 원문·오류 코드표·응용 프로그램 인터페이스(Application Programming Interface, API) 목록 등이 추가된다 | 자료가 없으면 AI가 그 자리를 추측으로 채운다(M2 실수 2) |
| | [형식] | 어떤 표를 요구하나 — 자금 흐름 표·원문 인용 표·책임 분계 표 등 유형 고유 표 1~2개 | 표의 열 이름이 곧 검토 기준이 된다(첫 열=기준, 끝 열=액션) |
| | [검증] | 무엇을 금지하나 — "승인 가능" 단정, "지급됩니다" 판단, 수익률 생성, 거래 사기 판단 등 | 유형별 환각 1곳을 검증 조건 한 줄로 막는다(M3 3원칙의 유형별 적용) |
| **같다** | 역할·목적·독자 | 문구만 바뀌고 구조는 같다 | 요청서의 뼈대는 업종과 무관하다 |
| | PRD 8섹션·두괄식·표 양식·지표 3종 | 그대로 | 읽히는 문서의 조건은 도메인과 무관하다(`prd-authoring-playbook`) |
| | 3관점 리뷰·별도 대화 검수·사람이 결정 | 그대로 | 리더십·디자이너·EM의 질문은 유형이 바뀌어도 같다 |
| | `[가정]`·`[확인 필요]`·"컴플라이언스 확인 필요" | 그대로 | 금융 문서의 정직성 표기는 공통 언어다 |

**노하우(왜)**: "우리 서비스는 마이데이터가 아니라 결제라서 오늘 내용이 안 맞는다"는 반응을 오후 1부 재시동(12:30)에서 미리 끊어야 한다. 바뀌는 것이 셋+셋뿐이라고 먼저 말하면, 수강생은 머니핏을 따라가면서도 자기 유형의 세 칸을 메모하게 된다. 은행·카드·보험사 프로젝트를 오갈 때도 모델과 데이터는 매번 달랐지만 문서의 뼈대와 검증 질문은 같았다 — 그 경험이 이 렌즈의 근거다.

## 2. 핀테크 서비스 유형 7종 렌즈표

### 2.0 한눈에

| # | 유형 | 대표 서비스(일반 명사) | 사용자 여정 3단계 | [검증]에서 반드시 막는 것 한 줄 | 머니핏과의 거리 |
|---|------|---------------------|-----------------|-------------------------------|---------------|
| 1 | 지급결제·송금 | 간편결제·송금 앱, 전자지급결제대행(Payment Gateway, PG), 선불 충전 | 결제 수단 등록·인증 → 결제·송금 실행 → 내역 확인·취소·환불·정기결제 관리 | 수수료·한도·정산일·환불 기한 숫자 생성 금지 | 중간 — 자동 저축(이체)이 접점 |
| 2 | 여수신·대출 | 비대면 대출·사전심사, 신용평가모형(Credit Scoring System, CSS)·대안신용평가, 카드·할부 | 사전심사 입력(동의·자료) → 결과·조건 확인 → 신청·실행·상환 관리 | "승인 가능" 단정·금리·한도 생성 금지, AI는 심사 결정을 하지 않음 | 중간 — 마이데이터 소득·거래 자료 활용이 접점 |
| 3 | 자산관리·마이데이터 | 개인 자산관리(Personal Financial Management, PFM), 가계부, 자산 통합 조회·코칭 — **머니핏** | 계좌·카드 연동(전송요구 동의) → 소비 분류·목표 설정 → 코칭·자동 저축·리텐션 | 금융상품 권유·수익률 약속으로 읽히는 문구 금지 | 기본형(0) |
| 4 | 투자·증권 | 로보어드바이저, 리서치 요약, 간편 투자 | 투자 성향 진단·계좌 개설 → 리서치·포트폴리오 제안 확인 → 주문·리밸런싱·보고 | 수익률·목표가 생성 금지, 매수·매도 권고 표현 금지, 출처 없는 문장 삭제 | 가까움 — 코칭이 권유로 넘어가는 경계가 같은 질문 |
| 5 | 보험 | 인슈어테크, 보험 비교·가입, 청구 접수·챗봇 | 보장 확인·상품 탐색 → 청구 접수(서류·챗봇) → 심사·지급·보완·이의 | 보장·지급 여부 판단 금지, 의료 판단 금지, 건강 정보는 가상 표기 | 멀다 — 민감정보(건강)와 약관 해석이 새 축 |
| 6 | 인증·보안·FDS·AML | 본인확인·인증, 이상거래탐지시스템(Fraud Detection System, FDS), 자금세탁방지(Anti-Money Laundering, AML) | 가입·고객확인(Know Your Customer, KYC) → 거래 시 인증·실시간 탐지 → 이상 시 차단·사람 검토·고객 안내·보고 | 개별 거래의 정상·사기 판단 금지(사람 검토), 보고 기한·양식은 [확인 필요] | 멀다 — 생성형 AI는 문서 보조, 판단은 규칙·모델·사람 |
| 7 | B2B·임베디드 금융·BaaS | 서비스형 뱅킹(Banking as a Service, BaaS), 응용 프로그램 인터페이스(Application Programming Interface, API) 제공, 파트너 내장 결제·대출 | 파트너 계약·심사·온보딩 → 연동 개발·테스트 → 운영·정산·모니터링·장애 대응 | 서비스 수준 협약(Service Level Agreement, SLA) 수치·API 필드·계약 문구 생성 금지, 인허가 보유 여부 판단 금지 | 멀다 — 독자가 고객이 아니라 파트너·개발자 |

> 표기 규칙: 아래 각 유형의 지표 수치는 전부 `[가정]`(교육용 예시값)이고, 규제 질문의 법·가이드는 **명칭·기관·연도만** 쓰며 조항 번호를 쓰지 않는다. 모든 규제 항목의 상태는 `[확인 필요]`. 대표 서비스는 일반 명사이며 특정 기업·상품을 가리키지 않는다.

### 2.1 지급결제·송금

| 항목 | 내용 |
|------|------|
| 사용자 여정 3단계 | ① 결제 수단 등록·본인 인증(카드·계좌·충전) → ② 결제·송금 실행(승인·이체·정기결제) → ③ 내역 확인·취소·환불·구독(정기결제) 관리 |
| 핵심 지표 3종 `[가정]` | 결제 성공률 `payment_success / payment_attempt` 96.0% → 98.0% · 결제 단계 이탈률 `checkout_abandon / checkout_start` 12% → 8% · 결제 관련 고객 응대(Customer Service, CS) 문의 `cs_ticket_payment`(결제 1천 건당) 15 → 9 · 확인 시점: 출시 후 8주 |
| 규제 체크 질문 | ① 우리 구조가 전자금융업 등록 대상(선불전자지급수단 발행·전자지급결제대행·전자자금이체 등)인가, 아니면 등록 사업자(PG·은행) 경유 구조인가(전자금융거래법 `[확인 필요]`) ② 선불충전금·이용자 자금의 별도 관리·보호 의무가 우리에게 적용되는가(전자금융거래법 2024.9 개정 시행으로 알려진 내용 `[확인 필요]`) ③ 정기결제(구독)의 결제 전 고지·해지 절차·환불 기준은 어떤 규정을 따르는가(전자상거래법·금융소비자보호법 `[확인 필요]`) ④ 해외 송금이 포함되면 소액해외송금업 등록과 자금세탁방지 의무는 어디까지인가(외국환거래법·특정금융정보법 `[확인 필요]`) |
| AI 활용점 | 오류 코드 → 고객 안내 문구 초안(비전공자 언어) · 정기결제·구독 내역 요약과 해지 경로 안내(정보 제공, 해지 실행은 사용자) · 결제 CS 1차 응대 스크립트(정책 문서 원문 대조) |
| 환각 위험이 큰 곳 1개 | **수수료·한도·정산 주기·환불 기한 숫자** — 자료에 없으면 그럴듯한 값이 생성된다. 고객 안내 문구에 들어가면 곧 민원이다 |
| [자료] 변형 | 5개 핵심 입력 + **결제 흐름도(단계·주체·자금 이동)** + **오류 코드표(가상)** + 수수료·정산·환불 정책(치환값) |
| [형식] 변형 | 8섹션 + **자금 흐름 표(단계 \| 주체 \| 자금 이동 \| 실패 시 처리)** + 오류·취소·환불 시나리오 표 + 고객 안내 문구 초안(성공·실패·환불 3종) |
| [검증] 변형 | "수수료·한도·정산일·환불 기한은 자료에 있는 값만 쓰고 없으면 `[확인 필요]`. 전자금융업 등록 대상 여부는 판단하지 말고 컴플라이언스 질문으로 남긴다. 실제 결제사·카드사를 평가하지 않는다" |

| [형식] 변형 | 8섹션 + **청구 단계 표(단계 \| 사용자 행동 \| 필요 서류 \| 실패·보완 시)** + **원문 인용 표(원문 그대로 \| 해당 동작 \| 컴플라이언스 질문)** + 상담사 전환 조건 표 |
| [검증] 변형 | "보장·지급 여부를 판단하는 문장을 쓰지 않고 '약관 원문 인용 + 담당자 확인'으로 바꾼다. 의료 판단을 하지 않는다. 실제 인물·병명 사례를 만들지 않는다(가상 표기). 결과 말미에 '본 결과는 법률·의학 자문이 아니며 컴플라이언스 확인 필요'를 그대로 쓴다" |
| 노하우(왜) | 보험 챗봇 PRD는 디자이너 관점 D3(잘못됐을 때의 대응)가 핵심이다. "모르면 상담사로 넘긴다"는 규칙을 §4 폴백 열과 §7 규제 질문 ④에 **같은 문장**으로 넣어야 3관점 리뷰에서 일관성이 나온다 |

### 2.6 인증·보안·FDS·AML

| 항목 | 내용 |

| 사용자 여정 3단계 | ① 가입·본인확인(KYC)·접근매체 등록 → ② 거래 시 인증·실시간 이상거래 탐지 → ③ 이상 시 차단·사람 검토·고객 안내·의심거래보고(Suspicious Transaction Report, STR) |

| 규제 체크 질문 | ① 본인확인·접근매체·인증 수단 요건과 사고 시 책임 분담 기준은 무엇인가(전자금융거래법·전자금융감독규정·전자서명법 `[확인 필요]`) ② 고객확인(KYC)·의심거래보고(STR)·고액현금거래보고(Currency Transaction Report, CTR) 의무가 우리 사업자 유형에 적용되는가, 보고 기한·양식은 무엇인가(특정금융정보법 `[확인 필요]`) ③ FDS 오탐으로 정상 거래를 차단했을 때 고객 안내·해제 절차와 설명 의무는 무엇이며, 생체·행동 데이터 사용은 민감정보 처리인가(개인정보보호법 `[확인 필요]`) ④ 탐지 모델 변경·재학습의 검증·승인 절차와 보안 요건은 무엇인가(금융보안원 「금융분야 AI 보안 가이드라인」(2023.4) `[확인 필요]` · 인공지능기본법 고영향 여부 `[확인 필요]`) |
| AI 활용점 | 이상거래 알림 사유 요약(검토자용, 사람 판단 보조) · 의심거래 검토 메모·보고서 **초안 구조화**(회사 승인 환경 전제) · 차단·해제 고객 안내 문구 — **판단은 규칙·모델·사람, 생성형 AI는 문서 보조** |
| 환각 위험이 큰 곳 1개 | **개별 거래의 정상·사기 판단과 보고 기한·양식·법령 조항** — 생성형 AI가 "이 거래는 사기입니다"라고 쓰는 순간 문서가 아니라 사고가 된다 |
| [자료] 변형 | 5개 핵심 입력 + **탐지 규칙·알림 유형 목록(가상)** + 사례 요약(가명·가상) + 운영 절차(치환값) |
| [형식] 변형 | 8섹션 + **오탐·미탐 시나리오 표(유형 \| 신호 \| 사람 검토 기준 \| 고객 안내)** + 검토자 체크리스트 + 안내 문구 2종(차단·해제) |
| [검증] 변형 | "개별 거래의 정상·사기 여부를 판단하지 않고 사람 검토 항목으로 남긴다. 보고 기한·양식·조항은 `[확인 필요]`. 실제 사고·인물 사례를 인용하지 않는다. 결과는 내부 검토용이며 고객에게 그대로 노출하지 않는다" |
| 노하우(왜) | 4회차의 FDS·AML 내용을 들었다면 `[확인 필요]`, 오늘의 차이는 하나다 — 탐지는 규칙·모델이 하고, 생성형 AI는 **검토자가 읽을 문서**를 빨리 만든다. 이 경계를 §4 표의 "사람 확인 필요 여부" 열에 전부 '예'로 써야 EM 관점 E5(보안·규제 요건)가 통과된다 |

## 3. 문서 관리 안정화 원칙 (모든 유형 공통) + 유형별 필수 추가 섹션

### 3.1 다섯 원칙

| # | 원칙 | 규칙 | 왜(노하우) |
|---|------|------|-----------|
| 1 | **계층과 SSOT** | 2-Pager(왜) → PRD(무엇, SSOT) → 명세(Spec)·상위 설계(High-Level Design, HLD)(어떻게) → 아키텍처 결정 기록(Architecture Decision Record, ADR)(왜 이렇게) → 운영(Ops). 하위 문서는 PRD의 **특정 섹션을 참조**하고 복사하지 않는다(Side Document 헤더) | 같은 사실이 두 문서에 있으면 하나는 반드시 낡는다. AI로 문서를 빨리 만들수록 복사 유혹이 커지므로 "참조만"을 규칙 파일에 박아 둔다 |
| 2 | **메타 헤더·Change Log** | 모든 문서 상단 6줄(Status·Document Type·Product·Last Updated·Last Author·Owner) + 문서 끝 접이식 Change Log(역순·구체적 변경·**AI 도구명 표기**) | "누가 어느 AI로 무엇을 바꿨나"가 남아야 리뷰어가 어디를 다시 볼지 안다. `Last Author: PM 홍길동 with Claude …` 표기는 책임을 사람에게 남기는 장치다 |
| 3 | **버전** | v0.1 초안(Draft) → v0.x 리뷰 반영(In Review) → **v1.0 승인(Approved)** → v1.x 승인 후 변경(Change Log 필수) → v2.0 범위 변경(2-Pager 재승인). 프롬프트 카드도 같은 규칙(`v1 · 날짜 · 도구명`) | 버전 없는 문서는 "어느 판을 보고 개발했나"를 말할 수 없다. 프롬프트도 문서이므로 같은 규칙을 적용한다(핵심 메시지 3) |
| 4 | **3관점 평가 게이트** | Approved 전환 조건: 리더십·디자이너·EM 3관점 모두 통과(레포 기준 관점당 30점 만점 20점 이상 + 항목 최소 점수 · 강의 축약판은 25점 만점 17점). AI 리뷰(별도 대화) → 사람 보완 → **사람이 결정** | 세 청중의 질문이 다르므로 한 사람의 "좋아 보인다"는 게이트가 아니다. 채점표를 먼저 정하는 이유는 대학원 과제 채점과 같다 — 순서가 바뀌면 인상 평가가 된다 |
| 5 | **규제 섹션은 질문 + 회신 기록 누적** | §7을 "판단"이 아니라 아래 3.2 양식의 **질의·회신 로그**로 운영. 회신은 요지만 적고 원문은 사내 시스템에, 회신자는 **역할**로만(실명·연락처 금지). 상태 열이 전부 '회신 완료' 또는 '조건부'가 되어야 v1.0 | 규제는 한 번 확인으로 끝나지 않고 릴리스마다 다시 묻는다. 로그로 누적하면 다음 PRD가 같은 질문을 처음부터 하지 않는다 |

| 보험 | **민감정보(건강) 처리 흐름과 최소 수집·상담사 전환 원칙** | 데이터·질문 유형 \| 수집 여부 \| 보관·전송 범위 \| 챗봇 응답 한계 \| 전환 조건 | 청구 챗봇은 민감정보와 약관 해석이 동시에 걸리는 유일한 유형 |
| 인증·보안·FDS·AML | **오탐·미탐 운영 기준과 사람 검토 절차·모델 변경 관리** | 시나리오 \| 신호 \| 사람 검토 기준 \| 고객 안내 \| 모델 변경 승인 | 모델은 확률을 내고 사람이 기준을 정한다 — 그 기준이 문서에 없으면 운영이 없다 |
| B2B·임베디드·BaaS | **책임 분계·SLA·감사 로그와 파트너 온보딩 심사** | 기능 \| 우리 책임 \| 파트너 책임 \| 규제 주체(질문) \| 감사 로그 \| SLA 항목 | 독자가 파트너이므로 "누가 무엇을 책임지나"가 시나리오보다 먼저다 |

> 프롬프트 반영법: [`lab-2 §B Step 2`](../workshop/lab-2-prd-draft.md) 프롬프트의 [형식] 8개 섹션 아래에 `9. (유형별 추가 섹션 이름) — 표: (위 양식)` 한 줄을 덧붙인다. 그 외는 바꾸지 않는다.

| 레벨 | 기법 | 오늘 어디서 | 수강생 실습(무료 웹) / 강사 시연 | 다음 레벨로 가는 신호 |

| **L2** 재요청·검증 루프 | 초안 → 결과 체크 3개 → 재요청 문장 1개 → **별도 대화** 검수(템플릿 f) → 수정 | M2 Step 3 · M3 실습 ②(11:00) | 실습 | 같은 재요청 문장을 매번 붙이고 있다 |

> 사다리와 발전 6단계(lab-3 §E)의 관계: **사다리 = 요청을 구조화하는 사람의 기술**, **6단계 = 도구가 맡는 범위**. L1~L3은 1 Chat·2 문서 생성에서 전부 가능하고, L4 = 3 템플릿화, L5 = 3~4 연결, L6 = 6 자율 실행형(Agentic)과 짝이다. 5 오피스 내장은 출력 채널이라 어느 레벨에서도 만난다. 금융권은 L4부터 회사 승인 환경이 필요할 가능성이 높다 `[확인 필요]` — 개인 계정에 회사 자료로 템플릿·컨텍스트를 만들지 않는다.

### 4.1 L1 — 6요소 카드(단발)

| 항목 | 내용 |
|------|------|
| 기법·왜 | 여섯 칸을 채운 **업무 요청서** 1회. 빈칸이 있으면 AI가 추측으로 채우고, 금융에서 그 추측이 환각이다. [검증] 한 줄("자료에 없는 숫자는 만들지 말고 `[확인 필요]`")이 없으면 나머지 다섯이 있어도 초안이 아니다 |
| 한 줄 예시(머니핏) | `[역할] 마이데이터 기반 핀테크 서비스 시니어 기획자 [목적] 프로덕트 리드가 PRD 본격 작성 여부를 결정 [독자] 리드+컴플라이언스, 5분 [자료] 5개 핵심 입력만 [형식] ①결론부터→⑦다음 액션, 지표 표·규제 표 열 고정 [검증] 자료에 없는 숫자·조항은 [확인 필요], 규제는 컴플라이언스 확인 필요, 마지막 문장은 요청` (전문: lab-1 §1.3) |
| 다음 레벨로 | 카드를 두 번째 실행할 때. 첫 답을 그대로 쓸 수 없다는 것이 **정상**이 된 순간 L2다 |
| 흔한 실패 | [자료]·[검증] 칸 생략 → 전부 추측 · 한 번에 다 요청 → 뒤가 뭉개짐 · 쿠션어·부정문 · 회사 원문을 그대로 붙임(30초 체크리스트 위반) |

### 4.2 L2 — 재요청·검증 루프(초안 → 검수 → 수정)

| 항목 | 내용 |
|------|------|
| 기법·왜 | 프롬프트를 통째로 다시 쓰지 않고 **재요청 문장 1개**(10선 — 1 없는 것 [확인 필요]+근거 · 2 결론 위로 · 3 표만 · 4 절반 · 5 근거 약한 3곳 · 6 독자 교체 · 7 규제→질문 · 8 마지막 열 시사점 · 9 지표 3종 · 10 검수 질문 5)로 고친다. 검수는 **새 대화**에서(템플릿 f) — 같은 대화에서 "맞지?"라고 물으면 동조한다. 교육 AI 서비스를 운영할 때 모델 출력 검증을 별도 단계로 두었던 습관이 그대로다 |
| 한 줄 예시(머니핏) | 재요청: `본문에서 자료에 없는 시장 규모·경쟁사·법령 문장을 모두 제거하고 확인 필요 목록으로 옮겨 주세요.` / 검수(새 대화): 템플릿 (f)에 초안 붙이기 → 오류 표(위치·유형·근거·수정안) |
| 다음 레벨로 | 같은 재요청 문장을 매번 붙이고 있다 → 그 문장을 카드의 [검증] 칸으로 **승격**(카드 v2). 리뷰 관점이 여러 개 필요하다 → L3 |
| 흔한 실패 | 같은 대화에서 검수 · 재요청 3회 이상(프롬프트 재설계 신호) · 재요청이 전체를 다시 쓰게 함("수정한 부분만 출력" 누락) · 검수 결과를 대조 없이 신뢰(검수도 AI다 — 정답표·원문 대조) |

### 4.3 L3 — 역할 분리 대화(작성자 / 리뷰어 3관점)

| 항목 | 내용 |
|------|------|
| 기법·왜 | 초안 대화(작성자) / **새 대화**(리뷰 패널: 리더십 L1–L5 · 디자이너 D1–D5 · EM E1–E5 채점표 → 점수·근거 인용·수정 제안 · 가장 약한 3곳) / 초안 대화로 복귀해 3곳만 보완 / **사람이 최소 출시 범위(P0)·지표·요청을 결정**. 세 청중은 서로 다른 질문을 하고, 채점표를 먼저 정해야 인상 평가가 안 된다. 커머스 Agentic 제품 PRD를 쓸 때 실제로 돌리는 루프다(개인 규칙, 회사 공식 양식 아님) |
| 한 줄 예시(머니핏) | 새 대화: `[역할] PRD 심사 리뷰 패널(리더십→디자이너→개발 리드) [목적] 10분 안에 고칠 약점, 칭찬 불필요 [자료] 아래 PRD 본문만 [형식] 관점별 표(항목·점수·근거 인용·수정 제안) + '가장 약한 3곳' 표(순위·약점·왜 위험·재요청 문장) [검증] PRD에 없는 내용 가정 금지, 규제는 컴플라이언스 확인 필요` (전문: lab-2 §B Step 3) |
| 다음 레벨로 | 같은 리뷰 프롬프트를 주 2회 이상 → L4 저장. 리뷰어가 매번 회사 용어·정책을 몰라 엉뚱한 지적 → L5 컨텍스트 |
| 흔한 실패 | 3관점을 작성자 대화에서 시킴 · 점수만 받고 근거 인용 없음 · 리뷰 결과를 전부 반영하려 함(3곳만) · 리뷰 점수가 곧 문서 품질이라는 착각(17점 미달이 정상인 10분 초안) |

### 4.4 L4 — 템플릿·프로젝트화(Projects·GPTs·Gems·Skills)

| 항목 | 내용 |
|------|------|
| 기법·왜 | 카드(a)~(g)와 리뷰 프롬프트를 도구의 재사용 기능(Claude Projects·Skills / ChatGPT GPTs·Projects / Gemini Gems — 무료 플랜 제공 여부·'지침' 칸 명칭 `[강의 전 확인]`)의 **지침**에 넣고, 대화에는 변수(《서비스명》《타겟》…)만 넣는다. "프롬프트는 문서다" — 저장·버전·공유가 생산성이고 팀원이 같은 규칙으로 일한다 |
| 한 줄 예시(머니핏) | 지침 = 카드 (a) 전문(《 》 라벨 유지) → 대화: `서비스: 머니핏 / 타겟: 25–35세 급여 직장인 [가정] / 문제: 파악 40분·목표 전 이탈 1/4 [가정] / AI 활용점: 분류·인사이트·코칭 / 성공 기준: set_goal 72.5→80% [가정]` 5줄만 |
| 다음 레벨로 | 매 요청에 같은 자료(용어집·데이터 딕셔너리·규제 질문 목록·회사 양식 섹션 제목)를 붙이고 있다 → L5 |
| 흔한 실패 | **개인 계정에 회사 자료로 템플릿 생성**(금융권 승인 환경 필요 `[확인 필요]`) · 버전 없이 지침 덮어쓰기(v1·날짜·도구명) · 지침이 길어져 규칙과 변수가 섞임(변수는 대화로) · 도구가 바뀌면 사라짐(원본은 문서 저장소 텍스트로 — 무료 대안이자 백업) |

### 4.5 L5 — 컨텍스트 파일(context/·데이터 딕셔너리·용어집)

| 항목 | 내용 |
|------|------|
| 기법·왜 | `context/`에 용어집(약어·한글·영문)·데이터 딕셔너리(이벤트·컬럼 정의)·규제 질문 목록 + 회신 로그(§3.2)·회사 양식 섹션 제목을 **버전 표기**로 두고 매 요청 [자료] 앞에 첨부(파일 업로드 가능 여부는 도구·플랜별 `[강의 전 확인]`, 무료 경로는 텍스트 붙이기). 딕셔너리를 먼저 주면 AI가 열 이름·지표 정의를 지어내지 않는다(M9 노하우). [자료]를 매번 손으로 쓰면 빠지고 팀마다 다르게 쓴다 |
| 한 줄 예시(머니핏) | `아래 데이터 딕셔너리(signup·link_account·set_goal·first_saving·d30_active 정의, v1 2026-09-18)와 용어집만 근거로, 연동 사용자 대비 set_goal 전환율을 계산 과정과 함께 표로 쓰고, 딕셔너리에 없는 컬럼·지표는 만들지 말고 [확인 필요]로 표시하세요.` |
| 다음 레벨로 | PRD ↔ 2-Pager ↔ 회의록 ↔ 슬라이드가 서로 참조하고 한쪽이 바뀌면 나머지를 손으로 고치고 있다 → L6 |
| 흔한 실패 | 딕셔너리 없이 CSV만 올려 열 의미를 추측하게 함 · 컨텍스트에 **실데이터·개인정보** 포함(가상·가명·치환만) · 버전 없는 컨텍스트(어느 판을 근거로 썼는지 모름) · 컨텍스트가 너무 길어 요청이 묻힘(요청과 관련된 파일만) |

### 4.6 L6 — 하네스(규칙 파일 + 폴더 + 완료 기준)

| 항목 | 내용 |
|------|------|
| 기법·왜 | 규칙 파일(CLAUDE.md/AGENTS.md: 범위·금지·표기 규칙·완료 기준 — **코드가 아니라 문서 규칙**) + 폴더(`context/`·`templates/`·`outputs/`) + 완료 기준(체크리스트)을 주고, AI가 문서를 **갱신하고 검증 결과를 보고**하게 한다(예: PRD 지표 표 수정 → 2-Pager·Change Log 갱신 → 3관점 체크리스트 통과 여부 표). 도구: Claude Code·Claude Desktop Cowork `[강의 전 확인]` — 오늘은 시연만. 모델은 바뀌고 규칙·검증 증거는 남는다 — 대학원 LLMOps(대규모 언어 모델 운영) 수업에서도, 이 강의 자료를 만들 때도 같은 원칙이다 |

| 다음 레벨로 | 여기가 끝이 아니다 — 규칙 파일 v1 → 팀 리뷰 → 갱신 루프. 온라인 과정 7강(클로드 코워크·스킬·커넥터)에서 더 깊게 |

## 5. 서비스 유형 × 레벨 적용 예시 3개 (교육용 가상 사례)

> 세 사례는 01-lecture-design §5의 대안 (B)·(C)와 보험 유형을 **핀트리(가상)의 확장 시나리오**로 만든 것이다. 서비스명·수치·구조는 전부 `[가정]`이며 실제 기업·상품과 무관하다. 내 서비스로 실습하는 수강생의 참고용(§6 장표 후보 7 = 부록 A4).

### 5.1 대출 사전심사 사용자 경험(User Experience, UX) PRD — "사장님핏(SajangFit)" (여수신·대출 렌즈 · 오늘 L1→L2, 월요일 L3, 다음 L5)

**5개 핵심 입력** (lab-2 §0-2 빈칸 카드 형식)

```text
1. 서비스명: 사장님핏(SajangFit) — 가상 회사 핀트리(FinTree)의 소상공인 매출 데이터 기반 비대면 대출 사전심사. 핀트리는 직접 대출을 실행하지 않고 제휴 금융사(가상 A은행)의 상품을 안내하는 구조로 가정한다 [가정]. 필요한 등록 유형은 컴플라이언스 확인 필요.
2. 타겟 유저: 영업 3년 미만, 월 매출 변동이 큰 소상공인(카페·소매) [가정]. 은행 창구 방문 시간이 없고, 서류 준비 단계에서 포기한 경험이 있다 [가정].
3. 핵심 문제: "내가 대출이 되는지 알아보는 데 서류 준비 3일과 방문 2회가 든다" [가정]. 사전심사 시작자의 55%가 서류 단계에서 이탈한다 [가정]. 원인 후보는 서류 파악 비용과 결과 예측 불가 [확인 필요].
4. AI 활용점: ① 업종·상황별 필요 서류·절차 안내 문구 ② 심사 결과 안내 문구 초안(승인·조건·거절 사유 코드 → 문장, 사람 승인 후 게시) ③ 매출 데이터 연동 오류 안내 — AI는 심사 결정을 하지 않는다(컴플라이언스 확인 필요).
5. 성공 기준(모두 [가정]):
   - 핵심 ① 사전심사 완료율(시작자 대비): Baseline 45% → Target 60% · 측정 이벤트 prequal_complete
   - 핵심 ② 결과 확인 → 신청 전환율: Baseline 30% → Target 38% · 측정 이벤트 loan_apply
   - 보조 ③ 서류 보완 재요청률: Baseline 35% → Target 20% · 측정 이벤트 doc_resubmit
   - 가드레일: 30일 이상 연체율(dpd30) 악화 금지 · 확인 시점: 출시 후 8주
```

### 5.2 간편결제 구독 관리 알림 PRD — "페이핏(PayFit) 구독 알림" (지급결제·송금 렌즈 · 오늘 L1→L2, 다음 L4→L5)

**5개 핵심 입력**

```text
1. 서비스명: 페이핏(PayFit) 구독 알림 — 가상 회사 핀트리(FinTree)의 간편결제 앱 안에서 정기결제·구독·자동이체를 한 화면에 모아 결제 전 알림과 해지 경로를 안내한다. 페이핏은 전자금융업자로 등록된 것으로 가정한다 [가정].
2. 타겟 유저: 구독 서비스를 4개 이상 쓰는 20–30대 [가정]. 해지한 줄 알았던 결제가 다음 달에 청구된 경험이 있다 [가정].
3. 핵심 문제: "결제되고 나서야 안다." 정기결제 후 3일 안의 환불·문의가 결제 관련 CS의 40%를 차지한다 [가정]. 해지 경로를 못 찾아 앱을 이탈한다 [가정]. 원인 후보는 결제 전 고지 부재와 가맹점별 해지 경로 분산 [확인 필요].
4. AI 활용점: ① 결제 내역에서 정기결제 자동 식별·월간 요약(규칙 + 모델) ② 결제 전 알림 문구 개인화(정보 제공) ③ 가맹점별 해지 절차 안내 문구(존재 확인 후 게시) — 해지 실행은 사용자가 한다.
5. 성공 기준(모두 [가정]):
   - 핵심 ① 결제 전 알림 확인율(발송 대비): Baseline 착수 시 측정 → Target 60% · 측정 이벤트 prebill_notice_open
   - 핵심 ② 정기결제 관련 CS 문의(결제 1천 건당): Baseline 15 → Target 9 · 측정 이벤트 cs_ticket_recurring
   - 보조 ③ 구독 관리 화면 30일 재방문율: Baseline 착수 시 측정 → Target 35% · 측정 이벤트 sub_manage_return_30d
   - 확인 시점: 출시 후 8주
```

| 규제 질문(§7) | 관련 법·가이드 | 상태 |
|--------------|--------------|------|
| 정기결제 결제 전 고지·해지 절차·환불 기준은 어느 규정을 따르는가 | 전자상거래법 · 금융소비자보호법 | `[확인 필요]` |
| 결제 내역을 분석해 정기결제를 식별·요약하는 것의 동의 근거와 외부 생성형 AI 전송 가능 범위는 | 개인정보보호법 · 신용정보법 · 개인정보위 「생성형 인공지능(AI) 개발·활용을 위한 개인정보 처리 안내서」(2025.8) | `[확인 필요]` |
| 결제 전 알림이 광고성 정보로 분류될 수 있는 조건과 수신 동의 요건은 | 정보통신망법 | `[확인 필요]` |

**레벨 적용**: 오늘 L1([자료]에 결제 흐름도·오류 코드표(가상)·환불 정책(치환), [형식]에 자금 흐름 표·알림 문구 3종, [검증]에 "수수료·환불 기한 숫자 생성 금지") → L2(재요청 1번으로 없는 정산일을 `[확인 필요]`로) → 다음 L4(**알림 문구 템플릿**을 GPTs·Gems·Projects `[강의 전 확인]`에 저장 — 매주 반복되는 문구 작업이 주 2회 이상 신호) → L5(가맹점별 해지 경로표를 `context/`에 존재 확인일과 함께).

### 5.3 보험 청구 챗봇 PRD — "보험핏(InsureFit) 청구 도우미" (보험 렌즈 · 오늘 L2→L3, 다음 L5)

**5개 핵심 입력**

```text
1. 서비스명: 보험핏(InsureFit) 청구 도우미 — 가상 회사 핀트리(FinTree)가 제휴 보험사(가상 B보험)의 실손 청구 접수를 안내하는 챗봇. 핀트리는 접수 안내·서류 체크까지만 하고, 심사·지급 판단은 보험사가 한다 [가정].
2. 타겟 유저: 연 1–2회 소액 실손 청구를 하는 30–40대 직장인 [가정]. 서류 이름을 몰라 병원을 두 번 방문한 경험이 있다 [가정].
3. 핵심 문제: 청구 시작자의 40%가 서류 단계에서 중단한다 [가정]. 접수 후 보완 요청이 35%다 [가정]. 콜센터 문의의 절반이 "어떤 서류가 필요한가"다 [가정]. 원인 후보는 서류 안내 분산과 약관 용어 [확인 필요].
4. AI 활용점: ① 사고·진료 유형별 청구 서류 체크리스트 안내 ② 약관 원문 대조 Q&A(원문 인용 + "담당자 확인" 문구 내장) ③ 접수 진행 상태 요약 — 보장·지급 여부 판단 금지, 상담사 전환 기준 내장(컴플라이언스 확인 필요).
5. 성공 기준(모두 [가정]):
   - 핵심 ① 청구 접수 완료율(시작자 대비): Baseline 60% → Target 75% · 측정 이벤트 claim_submit
   - 핵심 ② 서류 보완 요청률(접수 대비): Baseline 35% → Target 20% · 측정 이벤트 claim_doc_request
   - 보조 ③ 챗봇 → 상담사 전환율: Baseline 착수 시 측정 → 상한 30% · 측정 이벤트 handoff
   - 가드레일: 오안내 신고(misguide_report) 0 · 확인 시점: 출시 후 8주
```

| 규제 질문(§7) | 관련 법·가이드 | 상태 |
|--------------|--------------|------|
| 챗봇의 청구 안내·상품 언급이 보험모집에 해당하는가, 플랫폼 비교·추천 요건은 | 보험업법 · 금융소비자보호법 | `[확인 필요]` |
| 진료 내역·질병 정보(민감정보)의 수집·보관·외부 생성형 AI 전송 범위와 최소 수집 원칙은 | 개인정보보호법 · 신용정보법 | `[확인 필요]` |
| 실손보험 청구 전산화와 연계할 때 전송대행기관·의료기관 연동 요건은 | 보험업법 개정(2024.10 시행으로 알려짐) | `[확인 필요]` |
| "보장됩니다·지급됩니다" 안내가 약관 해석·지급 판단이 되지 않기 위한 문구 한계와 상담사 전환 기준은 | 보험업법 · 금융소비자보호법 · 보험사기방지 특별법 | `[확인 필요]` |

**레벨 적용**: 오늘 L2(초안 뒤 **새 대화 검수(템플릿 f)** 로 "지급됩니다"·병명 예시·조항 번호를 잡는다 — 이 유형은 검수가 곧 핵심 학습) → L3(3관점 리뷰에서 디자이너 D3 — 모르면 상담사로 넘기는 예외 시나리오가 §3·§4·§7에 같은 문장으로 있나) → 다음 L5(약관 원문(검토 범위)·서류 목록·회신 로그를 `context/`에 두고 매 요청 첨부 — 약관은 길어 텍스트 붙이기 한도 `[강의 전 확인]`, 검토 범위만 잘라 붙인다).
