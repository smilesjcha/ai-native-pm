## 결론부터

> **하네스(harness) = AI가 우리 팀처럼 일하게 만드는 문서 세트: 규칙 파일 + 컨텍스트 폴더 + 템플릿 + 완료 기준.**
> **프롬프트가 '문장'이라면 하네스는 '문서 구조'다.**

- 프롬프트는 한 번 잘 써도 다음 대화에서 사라진다. 하네스는 **파일로 남아** 새 대화·새 팀원·새 도구·새 모델이 와도 같은 방식으로 일하게 한다. 오늘 하루의 핵심 메시지 3번("프롬프트는 문장이 아니라 문서다")의 실체가 이것이다.
- 하네스는 개발자의 것이 아니다. 이 레포의 규칙 파일을 열어 보면 대부분이 **"숫자는 자료에 있는 값만, 목표는 [가정], 상위 문서부터 고친다, 실데이터 금지"** 같은 **문서 규칙**이다. 기획팀이 이미 말로 하고 있는 약속을 파일 한 장에 옮기는 일이다.
- 도입은 한 번에 하지 않는다. **0단계 개인 폴더 → 1단계 개인 규칙 1페이지 → 2단계 팀 용어집·템플릿 → 3단계 팀 규칙 + 리뷰 게이트 → 4단계 프로젝트 구조 표준화 → 5단계 자율 실행형(Agentic)**. 오늘 수강생은 0·1단계를 가져가고, 강사 시연(S3-27)이 5단계다.
- 금융권에서는 규칙 파일 첫 줄이 **"실데이터 금지 · 치환 · 검증"** 삼원칙이고, 하네스는 **회사 승인 환경**에서 만든다. 개인 계정에 회사 자료로 하네스를 만들지 않는다.

## 1. 하네스란 — 왜 프롬프트로는 부족한가

하네스(harness)는 마차에 말을 매는 장치다. 말(AI)의 힘은 그대로 두고, **어디로 어떻게 끌지**를 장치가 정한다. 강사의 직전 발표(`projects/26Q2_Claude-Code-Club-Talk`)의 한 줄 메시지 — "AI Native PM은 도구가 아니라 마구(harness)를 다듬는 사람" — 를 기획팀 언어로 풀면 아래 네 가지 문서다.

| 구성 요소 | 무엇인가 | 없으면 생기는 일(왜 필요한가) | 오늘 강의에서 이미 만든 것 |
|-----------|---------|------------------------------|--------------------------|
| **규칙 파일** | AI에게 주는 팀 업무 매뉴얼 1페이지(`CLAUDE.md`·`AGENTS.md` 같은 텍스트 파일) | 새 대화마다 같은 주의사항을 다시 붙여넣는다. 팀원마다 AI가 다르게 일한다 | 오늘 프롬프트마다 넣은 **[검증] 문장들**(근거 요청·[확인 필요] 표시·원문 대조) |
| **컨텍스트 폴더** | AI가 읽어야 할 입력 자료: 정책·용어집·데이터 딕셔너리·회신 기록(`context/`) | 매번 자료를 찾아 붙인다. AI가 모르는 용어를 지어낸다 | `workshop/sample-data/README.md`(데이터 딕셔너리)·머니핏 5개 핵심 입력 카드 |
| **템플릿** | 반복 요청을 저장한 프롬프트·문서 양식(`templates/`, 도구의 저장 기능) | 좋은 프롬프트가 개인 메모에만 있다. 버전이 갈린다 | 산출물 ① 템플릿 카드, 금융 템플릿 3종, 3관점 리뷰 프롬프트, 회의록·이메일·아웃라인 프롬프트 |
| **완료 기준** | "다 됐다"를 사람이 판단하는 체크리스트(규칙 파일의 마지막 절 또는 별도 파일) | AI가 스스로 "완료"라고 말하고 사람이 그대로 믿는다 | 실습마다 있던 **"결과 확인 3개"**·페어 체크리스트·3관점 평가 통과 조건 |

**프롬프트와 하네스의 차이 (한 표로)**

| 기준 | 프롬프트 | 하네스 |
|------|---------|--------|
| 형태 | 문장(한 번의 요청) | 문서 구조(폴더 + 파일) |
| 수명 | 그 대화 안 | 대화·모델·도구가 바뀌어도 남는다 |
| 소유 | 개인 | 팀(문서 저장소에 있고 리뷰된다) |
| 검증 | 결과를 보고 사람이 느낌으로 판단 | 완료 기준 파일에 대고 확인 |
| 개선 | 다음에 더 잘 써 보자 | 사고·실패에서 배운 것을 규칙 1줄로 추가(Change Log에 남긴다) |

> **노하우**: 규칙 파일이 길어지는 순서는 언제나 "사고 → 규칙 1줄"이다. 처음부터 완벽한 규칙을 쓰려 하지 말고, 이번 주 AI 결과에서 틀렸던 것 하나를 규칙 1줄로 바꾸는 일을 매주 반복한다. 이 레포의 `claude.md` 제약 5개도 그렇게 쌓였다.

## 2. 문서 구조 표준 — 폴더 트리와 각 폴더의 역할·소유자·갱신 주기

### 2.1 이 레포의 실제 트리 (살아있는 예시)

루트 `CLAUDE.md` §Document Structure를 그대로 인용한다. 프로덕트 매니저(Product Manager, PM) 조직의 제품 요구사항 정의서(Product Requirements Document, PRD)·설계·운영 문서를 **소스 코드 없이** 관리하는 순수 마크다운 레포다. 트리에 나오는 약어: 단일 진실 원천(Single Source of Truth, SSOT) · 사용자 경험(User Experience, UX) · 상위 설계(High-Level Design, HLD) · 상세 설계(Low-Level Design, LLD) · 아키텍처 결정 기록(Architecture Decision Record, ADR) · 엔지니어링 매니저(Engineering Manager, EM) · 응용 프로그램 인터페이스(Application Programming Interface, API).

```text
ai-native-pm/
├── CLAUDE.md                  ← 규칙 파일: 네이밍·구조·권한·작성 표준·3관점 평가 (Claude용)
├── GUIDE.md                   ← 사람용 빠른 시작 가이드 (역할별)
├── README.md                  ← 초기 설정 안내
│
├── context/                   ← AI 입력 자료 (팀 산출물이 아니라 AI에게 주는 재료)
│   ├── company-policies/      ← 전사 정책·조직도·의사결정 기준
│   ├── domain-knowledge/      ← 서비스별 도메인 지식·용어집
│   └── external-services/     ← 외부 API·파트너 연동 제약
│
├── docs/
│   ├── guides/                ← 작성 가이드·문서 계층 설명
│   ├── templates/             ← Master PRD·2-Pager 템플릿
│   ├── evaluation/            ← 3관점 평가 기준 (리더십·디자이너·EM)
│   ├── references/ planning/ decisions/
│
├── projects/                  ← 활성 프로젝트 (분기 prefix + Title-Case, 중첩 금지)
│   └── 26Q3_Example-Project/
│       ├── _index.md          ← Document Map (필수)
│       ├── claude.md          ← 프로젝트 전용 규칙·컨텍스트 (필수)
│       ├── prd/PRD.md         ← L1 SSOT · prd/2pager.md
│       ├── specs/             ← L2 UX·출력 명세
│       ├── decisions/         ← L2 hld/HLD.md · lld/ · adr/ADR-NNN-name.md
│       ├── ops/               ← L3 출시·운영
│       ├── assets/            ← screens/ wireframes/ prd/ references/
│       └── analysis/          ← notebooks/ outputs/
│
└── archive/                   ← 완료 프로젝트 (분기별 폴더, 구조 원본 유지)
```

이 강의 프로젝트 폴더(`projects/26Q3_AI-Native-PM/`)도 같은 원리다: `claude.md`(Claude용 규칙) · `agents.md`(Codex용 규칙) · `source/`(원 요구사항 = SSOT) · `planning/`(01 원칙 → 03 목차 → 04~06 상세, 상위→하위) · `workshop/`(프롬프트 전문의 단일 원본) · `references/`(벤치마크) · `assets/`(산출물). 강의 문서도 PRD처럼 **위계·SSOT·소유권**을 둔다.

### 2.2 폴더별 역할·소유자·갱신 주기 — 금융 기획팀 적용판

아래 "금융 기획팀 예시"는 모두 **가상 회사 핀트리(FinTree)** 기준이다. 소유자·주기는 권장값이다.

| 폴더/파일 | 무엇을 넣나 | 소유자(권장) | 갱신 주기(권장) | 금융 기획팀 예시(핀트리, 가상) |
|-----------|-----------|-------------|---------------|-------------------------------|
| **규칙 파일** `CLAUDE.md` / `AGENTS.md` / (선택) `skills.md` | 목적 · 대상·톤 · 문서 표준 · 네이밍 · 작업 순서 · 파일 소유권 매핑 · 금지·보안 · 완료 기준 (§3) | 팀 리드 PM 1인(공동 편집은 리뷰로) | 분기 1회 정기 + **사고·오류 발생 즉시 1줄** | `CLAUDE.md`(팀 규칙 1페이지), `AGENTS.md`(다른 도구용 동일 규칙), `skills.md`(재사용 프롬프트 목록·이름·용도) |
| `context/company-policies/` | 전사 정책·조직도·의사결정 기준·보안 정책 요약 | 컴플라이언스·정보보호 담당과 **협의한 PM** | 정책 변경 시(원본 링크·기준일 명시) | `genai-usage-policy.md`(회사 생성형 AI 이용 정책 **요약** + 원본 링크) · `regulation-summary.md`(마이데이터·신용정보법·개인정보보호법·전자금융거래법·금융소비자보호법 — **기관·문서명·연도 + `[확인 필요]`**, 법률 판단 없음) · `compliance-qa-log.md`(컴플라이언스에 물어본 질문과 **회신 요약** — 날짜·질문·회신 요지·적용 범위, 담당자 실명 없음) |
| `context/domain-knowledge/` | 서비스 비즈니스 규칙·용어집·데이터 딕셔너리·고객 여정 | 도메인 담당 PM + 데이터 담당 | 월 1회 점검, 지표 정의 변경 시 즉시 | `glossary.md`(마이데이터·전송요구권·가명정보·퍼널·코호트 등 한글(English, 약어) 병기) · `data-dictionary-events.md`(이벤트명·정의·측정 시점 — `workshop/sample-data/README.md`가 원형) · `moneyfit-service-overview.md`(5개 핵심 입력) |
| `context/external-services/` | 외부 API·파트너·인증 제약 **요약** | 연동 담당 PM | 연동 변경 시 | `mydata-relay-constraints.md`(중계 구조·호출 한도 — 수치는 `[확인 필요]`) · `auth-provider-notes.md` |
| `docs/guides/` | 문서 작성 가이드·문서 계층·정렬 플레이북 | 팀 리드 PM | 반기 1회 | 레포의 `prd-authoring-playbook.md`·`document-hierarchy.md`·`stakeholder-alignment-playbook.md` 그대로 채택 |
| `docs/templates/` | PRD·2-Pager·회의록·리서치 브리프 템플릿 | 팀 리드 PM | 분기 1회(버전 표기) | `master-prd-template.md`·`2pager-template.md` + 오늘 `workshop/prompt-templates-fintech.md`의 템플릿 3종 |
| `docs/evaluation/` | 3관점 평가 기준(리더십·디자이너·EM)과 평가 프롬프트 | 3관점 대표 각 1인 | 반기 1회 | `eval-leadership.md`·`eval-design.md`·`eval-engineering.md` + 금융 추가 항목 "규제·리스크 섹션 존재 여부" |
| `projects/YYQ#_Name/` | `_index.md` · `claude.md` · `prd/PRD.md`(SSOT) · `prd/2pager.md` · `specs/` · `decisions/`(HLD·LLD·ADR) · `ops/` · `assets/` · `analysis/` | 프로젝트 PM | 매 변경(Change Log 1행) | `26Q3_MoneyFit-Goal-Coaching/` — `prd/PRD.md`가 유일한 기준, 임원 요약은 `prd/2pager.md`, 규제 질문은 `decisions/adr/ADR-001-mydata-scope.md` |
| `archive/YYQ/` | 종료 프로젝트(구조·네이밍 원본 유지) | 팀 리드 PM | 분기 말 1회 | `archive/26Q2/…` |

**원칙 3개**

1. **`context/`는 산출물이 아니라 재료다.** 팀이 만든 결과(`projects/`)와 AI에게 주는 입력(`context/`)을 섞지 않는다. 섞이면 AI가 초안을 근거로 초안을 쓴다.
2. **깊이는 이해할 수 있는 만큼만.** 프로젝트 폴더는 `projects/` 바로 아래 flat, 이름이 길어져도 `-`로 잇는다(`❌ projects/ai/recommendation/`). 계층이 깊어지면 사람이 못 찾고, AI도 못 찾는다.
3. **한 레이어에 기준 문서 하나.** `PRD.md`·`HLD.md`처럼 `UPPER.md` 하나가 SSOT이고 나머지는 참조한다. 두 곳에 같은 내용을 쓰면 반드시 한 곳이 틀린다.

## 3. 규칙 파일 작성법 — 8개 섹션과 핀트리 예시 전문

### 3.1 8개 섹션 템플릿

| # | 섹션 | 무엇을 쓰나 | 왜 필요한가 | 이 레포에서의 실물 |
|---|------|-----------|-----------|-----------------|
| 1 | **목적** | 이 저장소·팀이 무엇을 만드는지 2줄, AI의 역할(보조자) | AI가 맥락 없이 일반론을 쓰는 것을 막는다 | 루트 `CLAUDE.md` "Repository Purpose", 프로젝트 `claude.md` "프로젝트 목적" |
| 2 | **대상·톤** | 독자, 언어, 약어 병기 규칙, 두괄식 | 임원용·개발자용 문서 톤이 매번 흔들리지 않게 | "한국어 기본, 산업 표준 용어 영어 병기" |
| 3 | **문서 표준** | 메타 헤더·Change Log·작성자 표기·`[가정]`/`[확인 필요]` 태그 | AI가 고친 문서를 사람이 추적할 수 있게(§4) | "Document Authoring Standards" |
| 4 | **네이밍** | 폴더·파일·프로젝트·SSOT 파일 패턴 4개 + 흔한 실수 | 검색·링크·자동화가 깨지지 않게 | "Naming Governance" |
| 5 | **작업 순서** | 무엇을 먼저 읽고, 어떤 순서로 고치며, 어디서 멈추는지 | AI가 하위 문서만 고쳐 상위와 어긋나는 사고를 막는다 | 프로젝트 `claude.md` "작업 순서(반드시 이 순서)" |
| 6 | **파일 소유권** | "바꾸고 싶은 것 → 수정할 파일" 매핑표 | 같은 내용이 두 파일에 생기는 것을 막고, 질문 없이 바로 일하게 | 프로젝트 `agents.md` 매핑표(벤치마크: `references/harness/how-to-work-better-worklife-ax-workshop/AGENTS.md`) |
| 7 | **금지·보안** | 실데이터·실명·연락처·키 금지, 범위 밖 파일 금지, 외부 전송 금지 | 금융권 필수. "하지 마라"는 프롬프트보다 규칙 파일에서 더 잘 지켜진다 | "제약 사항(반드시)" 1·4, "Permission Policy" Deny 목록 |
| 8 | **완료 기준** | 산출물별 "다 됐다"의 조건 + 마지막 보고에 남길 것 | AI의 "완료" 선언을 사람이 검증 가능한 문장으로 바꾼다 | `references/harness/how-to-work-better-samcheok-codex-demo/completion-criteria.md`, `agents.md` "완료 보고" 문장 |

### 3.2 금융 기획팀용 예시 규칙 파일 전문 (가상 회사 핀트리)

> 아래는 **교육용 가상 사례**다. 실제 회사·상품·수치가 아니다. 코드가 한 줄도 없다는 점을 확인하며 읽는다. 팀에 맞게 1페이지 안에서 고쳐 쓴다.

```markdown
# 핀트리 서비스기획팀 — AI 작업 규칙 (CLAUDE.md · 교육용 가상 사례)

## 1. 목적
- 이 저장소는 핀트리 서비스기획팀의 기획 문서(2-Pager·PRD·회의록·보고 자료)를 관리한다.
- AI는 초안·리뷰·요약을 돕는 보조자다. 결정·승인·대외 발송은 사람이 한다.

## 2. 대상·톤
- 독자는 기획자·디자이너·개발 리드·컴플라이언스 담당자다. 한국어 두괄식, 약어 첫 등장은 '한글(English, 약어)'.

## 3. 문서 표준
- 모든 문서 상단에 메타 헤더 6줄, 하단에 접이식 Change Log. 작성자는 '역할 이름 with AI 도구명'.
- 수치는 자료에 있는 값만 쓴다. 목표·추정은 [가정], 확인 전 정보는 [확인 필요].
- 규제·법령 문장은 기관·문서명·연도를 쓰고 [확인 필요]를 붙인다. 법률 판단은 "컴플라이언스 확인 필요"까지만.

## 4. 네이밍
- 폴더·파일은 kebab-case, 프로젝트 폴더는 YYQ#_Title-Case, 레이어 기준 문서는 PRD.md처럼 UPPER.md.

## 5. 작업 순서
1. context/의 용어집·데이터 딕셔너리·컴플라이언스 회신 기록을 먼저 읽는다.
2. prd/PRD.md(SSOT)를 고친 뒤 하위 문서(specs·ops)를 갱신한다. 역순 금지.
3. 변경마다 Change Log 1행을 남기고 Status는 바꾸지 않는다(Status는 사람이 바꾼다).

## 6. 파일 소유권 (바꾸고 싶은 것 → 수정할 파일)
- 요구사항·지표 → prd/PRD.md · 임원 요약 → prd/2pager.md · 용어 → context/domain-knowledge/glossary.md
- 규제 질문·회신 → context/company-policies/compliance-qa-log.md (회신은 요약만, 담당자 실명 금지)

## 7. 금지·보안
- 실제 고객·거래·계좌·내부 지표를 어떤 파일에도 넣지 않는다. 샘플은 가상으로 만들고 "가상 데이터"를 표기한다.
- 실데이터가 꼭 필요하면 치환(가명·구간값)한 뒤 쓰고, 결과는 원본과 대조해 검증한다.
- 이 저장소 밖의 파일 수정·외부 전송·개인 계정 연동은 하지 않는다.

## 8. 완료 기준
- PRD 초안: 두괄식 결론 블록, 지표 3종(Baseline→Target→측정 이벤트), 규제·리스크 섹션, [가정]/[확인 필요] 표기가 있다.
- 3관점 리뷰(리더십·디자인·엔지니어링)를 별도 대화로 받고 점수·미달 항목·수정 제안 표를 남긴다.
- 마지막 메시지에 바꾼 파일 경로·변경 이유·확인되지 않은 항목 목록을 쓴다.
```

### 3.3 Claude용·Codex용을 따로 두는 이유, 그리고 공통 규칙 분리

| 질문 | 답 |
|------|-----|
| 왜 파일이 두 개인가 | 도구마다 **자동으로 읽는 파일 이름 규약**이 다르다. Claude Code는 `CLAUDE.md`, OpenAI Codex 등 AGENTS 규약을 따르는 에이전트는 `AGENTS.md`를 읽는다 `[강의 전 확인]`. 이름이 다르면 못 읽고, 못 읽으면 규칙은 없는 것과 같다 |
| 내용도 달라야 하나 | **대부분 같아야 한다.** 다른 것은 도구별 실행 방법(명령·빌드·검증 절차)과 그 도구에게만 맡기는 작업(예: 캡처·삽입 워크플로)뿐이다. 벤치마크 `references/harness/how-to-work-better/`는 `CLAUDE.md`(원칙 6·명령·품질 검수(Quality Assurance, QA))와 `AGENTS.md`(작업 규칙 6·검증 명령)를 두고 **콘텐츠·보안·품질 게이트는 `common-guidelines.md` 한 곳**에 뒀다 |
| 충돌하면 | 우선순위를 **파일 첫 줄에 적는다.** 이 프로젝트 `agents.md` 첫 줄: "충돌 시 레포 루트 `CLAUDE.md` → 이 폴더 `claude.md` → 이 파일 순". 벤치마크는 반대로 공통 문서가 최우선이다. 어느 쪽이든 **적어 두는 것**이 중요하다 |
| 비개발 팀은 어디에 두나 | 웹 도구에서는 Claude Projects·ChatGPT GPTs/Projects·Gemini Gems의 **'지침(instructions)' 칸**이 규칙 파일 자리다 `[강의 전 확인]`. 팀 공유는 위키·문서 저장소의 **텍스트 파일**로 — 오늘 본 `AGENTS.md`도 텍스트 파일일 뿐이다 |
| `skills.md`는 무엇인가 | 재사용 프롬프트(오늘의 템플릿 카드들)의 **목록·이름·용도·입력·출력**을 적은 색인이다. 도구의 저장 기능(Skills·GPTs·Gems)으로 옮기기 전에 텍스트로 먼저 정리한다. 개인 계정에 회사 자료로 만들지 않는다 |

**작성 팁 5**: ① 1페이지(40줄 안) — 길면 읽히지 않는다 ② 금지보다 "대신 이렇게"를 함께 쓴다(`❌ prd.md → ✅ PRD.md`) ③ 숫자 규칙은 예시와 함께(`[가정]` 표기 예) ④ 사고 1건 = 규칙 1줄, 날짜와 함께 Change Log에 ⑤ 강사가 실제로 소리 내어 읽을 수 있는 문장만 남긴다(`CONTENT_HARNESS.md` §8 변경 기록 원칙).

## 4. 문서 안정화 메커니즘 — AI가 고쳐도 사람이 추적 가능하게

AI가 문서를 빠르게 고칠수록 **"누가·언제·무엇을·어떤 근거로"** 바꿨는지가 흐려진다. 아래 장치들은 그 추적성을 문서 구조 안에 심는다. 모두 이 레포 `CLAUDE.md`에 있는 것이다.

| 장치 | 무엇 | 왜(어떤 사고를 막나) | 이 레포 실물 |
|------|------|-------------------|-------------|
| **메타 헤더 6줄** | Status · Document Type · Product · Last Updated · Last Author · Owner | 어느 문서가 살아있는지, 누구에게 물어야 하는지 첫 줄에서 알게 | 모든 `planning/*.md` 상단 |
| **접이식 Change Log + AI 도구명** | 역순 표, 작성자 `PM 홍길동 with Claude Fable 5.1` / `(직접 작성)`, "내용 업데이트" 금지·구체 서술 | AI가 바꾼 문장과 사람이 바꾼 문장을 구분. 리뷰 시 "무엇이 왜 바뀌었나"를 파일 안에서 읽게 | `03-curriculum-outline.md` Change Log 2행(초안 → 교차 검수 반영, 바뀐 모듈·항목 열거) |
| **상위→하위 갱신 순서** | 원칙(01) → 목차(03) → 상세(04~06) → 실습(workshop) → 슬라이드 플랜(09) → PPT 코드. 역순 금지 | 하위만 고쳐 상위와 어긋나는 "두 개의 진실" 방지 | 프로젝트 `claude.md` "작업 순서(반드시 이 순서)" |
| **SSOT 참조 링크** | 기준 문서 하나(`PRD.md`, `source/kmac-m5-brief.md`), 다른 문서는 링크로 참조하고 복사하지 않는다 | 복사본이 늙어 틀린 근거가 되는 것 방지 | `docs/guides/document-hierarchy.md` "참조하되 복사하지 않는다", `03` 상단 "상위 문서" 링크 |
| **Side Document 헤더 3줄** | `> Side Document — prd/PRD.md의 보조 문서 / 참조 원본: PRD §섹션 / 목적: 한 줄` | 보조 문서가 어느 원본의 어느 절을 깊게 파는지 명시 → AI가 보조 문서를 독립 문서로 오해하지 않게 | `CLAUDE.md` "Side 문서 표준 헤더" |
| **상태 머신(Status)** | Draft → In Review → Approved(/Accepted) → Deprecated. **Status는 사람만 바꾼다** | AI가 "완료"를 선언해도 문서 상태는 바뀌지 않게 | 규칙 파일 예시 §5-3 |
| **3관점 평가 게이트** | `Approved` 조건 = 리더십·디자이너·EM 3관점 **모두 통과**(각 관점 30점 만점 중 20점 이상 + 항목별 최소 점수 — `CLAUDE.md`·`docs/evaluation/` 기준; `GUIDE.md`의 가중 35점 표기와 불일치 `[확인 필요]`) | 한 사람의 취향이 아닌 **파일에 적힌 기준**으로 통과·미달을 말하게. AI 리뷰도 같은 파일을 읽는다 | `docs/evaluation/eval-*.md` 3개 + 하단 "Claude 평가 프롬프트" |
| **리뷰 체크리스트 파일** | 열린 결정을 번호(E1, E2…)로 등록 → 선택지 → 권장안 → 반영 상태 → 관련 파일 | 결정이 채팅에 흩어지지 않게. AI가 "권장안대로 반영"했는지 사람이 대조 | `planning/00-review-checklist.md`(E1~E16, 반영 상태 표기) |
| **표기 태그** | `[가정]` `[확인 필요]` `[강의 전 확인]` | AI가 만든 숫자·사실을 확인된 사실과 구분. 검색 한 번으로 미확인 항목을 모은다 | 모든 `planning/`·`workshop/` 문서 |

**한 장으로 보는 흐름**

```text
AI가 문서를 고친다
  → Change Log 1행 (날짜 · 역할 이름 with AI 도구명 · 무엇을 왜)
  → 상위 문서부터 하위로 갱신 (SSOT 링크 확인)
  → [가정]/[확인 필요] 남은 항목 검색
  → 사람 리뷰 (리뷰 체크리스트에 열린 결정 등록)
  → 3관점 게이트 통과 시 사람이 Status를 Approved로 변경
```

> **노하우(왜 Change Log에 도구명까지 쓰나)**: 모델은 6개월마다 바뀐다. "이 절은 Claude Fable 5.1이 2026-09-18에 썼다"가 남아 있으면, 나중에 그 모델 특유의 오류 패턴(예: 규제 조항 지어내기)이 발견됐을 때 **어느 문서를 다시 검수할지** 검색으로 찾을 수 있다. 사람 이름만 있으면 못 찾는다.

## 5. 단계적 도입 로드맵 — 0단계에서 5단계까지

"발전 6단계"(lab-3 §E)가 **도구 사용 수준**의 선택 기준이라면, 아래는 **문서 구조 도입 순서**다. 단계를 건너뛰지 않는다 — 특히 2·3단계(팀 용어집·규칙·게이트) 없이 5단계(자율 실행형)로 가면 AI가 빠르게 틀린 문서를 만든다. 소요는 모두 `[가정]`(강사 경험 기반 권장값)이다.

| 단계 | 무엇을 만드나 | 소요 `[가정]` | 전제(보안 승인 등) | 첫 산출물 | 실패 신호(이게 보이면 이 단계로 되돌아간다) |
|------|-------------|--------------|-------------------|----------|------------------------------------------|
| **0. 개인 폴더** | `context/`(자료·데이터 딕셔너리) · `templates/`(프롬프트) · `outputs/`(결과) 폴더 3개 | 30분 | 없음. 단, **회사 자료는 회사 승인 환경에서만**, 개인 기기에는 공개 가능한 자료·가상 자료만 | 데이터 딕셔너리 1개 + 오늘 템플릿 카드 3개 + 회의록 결과 1개 (= 오늘 실습 키트 폴더가 예시) | 한 달 뒤 `outputs/`만 늘고 `templates/`가 안 는다(= 아직 프롬프트를 매번 새로 쓴다) |
| **1. 개인 규칙 파일 1페이지** | §3 8섹션 중 **목적·문서 표준·금지·완료 기준 4개**만 채운 `my-rules.md` | 1시간 + 매주 10분 | 없음 | 규칙 1페이지(20줄 안) — 오늘 프롬프트의 [검증] 문장들을 옮겨 적기 | 새 대화마다 규칙을 다시 붙여넣고 있다 / 규칙 파일이 3페이지를 넘었다 |

**오늘 수강생의 위치와 월요일 첫걸음**

- 오늘 실습 키트(`workshop/`)는 **0단계의 완성 예시**다: `sample-data/`(context) · `prompt-card-deck.md`(templates) · 각자 저장한 결과(outputs).
- 월요일에 할 일은 실습 ④의 "월요일 실행 1개"에 **1단계 규칙 4줄**을 덧붙이는 것이다: 목적 1줄 · 문서 표준 1줄(`[가정]`/`[확인 필요]`) · 금지 1줄(실데이터 금지) · 완료 기준 1줄(결과 확인 3개).
- 2단계 이상은 **팀·회사의 결정**이다. 첫 액션은 정보보호 부서에 "생성형 AI 입력 허용 문서 범위"와 "승인된 도구·계정"을 문의하는 것이다.

**자가 진단 3질문(발전 6단계와 공통)**: 같은 요청을 주 2회 이상 하는가(반복 횟수) · 매번 붙이는 자료가 3개 이상인가(파일 수) · 회사 승인 환경이 있는가(승인). 셋 중 둘 이상이 "예"일 때 다음 단계를 고른다.

## 6. 금융권 특화 주의 — 규칙 파일에 반드시 들어가는 것
