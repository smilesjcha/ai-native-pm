# 2026년 2학기 LLMOps 운영 커리큘럼

> 과목 운영안 · 프로젝트 기반 누적 산출물 · 8주차 기획서와 기말 프로젝트의 연결

## 과목 방향

이 과목은 거대 언어 모델 운영(Large Language Model Operations, LLMOps)을 개별 기술 목록이 아니라 **문제 정의 → 실행 추적 → 비교 평가 → 운영 판단 → 버전 개선**의 반복 과정으로 다룬다. 수강생은 매주 작은 산출물을 만들고, 이를 8주차 기말 프로젝트 기획서와 최종 포트폴리오로 연결한다.

- 수강 대상: 특정 대학에 한정하지 않는 대학생·대학원생 대상 통합 강좌
- 수업 방식: 16주 전체 대면 수업 없이 온라인으로 운영하며, 정규 수업은 실시간 강의를 원칙으로 진행
- 8주차: 중간고사와 실시간 강의 없이 기말 프로젝트 기획서 0.1을 온라인으로 제출·평가
- 16주차: 실행 가능한 서비스, 평가 결과, 운영 판단, 발표와 포트폴리오를 실시간 온라인으로 공유
- 학습 방식: 이론, 현업 사례, 실습, 문서화, 교수 질의응답, 수정 이력
- 교수 소개: 차성재 · 무신사 Core AI PM × AI 대학원 겸임교수
- 역할명 약어: Artificial Intelligence(AI) · Product Manager(PM)

배점, 제출 시각, 팀 구성과 제출 형식의 최종 기준은 소속별 수업·과제 공지를 따른다.

2주차부터 격주로 과제를 안내하며 출제 후 일주일 이내 제출한다. 첫 과제는 2026년 9월 11일 출제, 9월 18일 이내 제출이다. 소속별 온라인 학습관리시스템(Learning Management System, LMS) 또는 교수자 이메일로 제출하며, 정확한 경로는 [과제 01 제출 안내](../../week02/ASSIGNMENT_01.md#제출-경로와-일정)를 확인한다. 공개 GitHub에는 과제나 개인정보를 올리지 않는다. 8주차 기획서·16주차 발표가 있는 주차의 별도 과제 여부와 배점은 개별 공지를 우선한다.

## 학습성과

수강생은 16주 종료 시 다음을 수행할 수 있다.

1. 사용자와 업무 의사결정을 기준으로 LLM 서비스 문제를 정의한다.
2. 프롬프트, 검색 맥락, 모델, 코드, 설정과 정책의 버전을 구분한다.
3. 응용 프로그래밍 인터페이스(Application Programming Interface, API)와 실행 추적(trace)을 이용해 재현 가능한 서비스를 구성한다.
4. 품질, 지연시간, 비용, 안전성과 재현성의 평가 기준을 설계한다.
5. 실패 유형과 복구 경로를 포함한 운영 구조를 설명한다.
6. 교수 질의응답을 통해 가정을 검토하고 수정 이유를 의사결정 기록으로 남긴다.
7. 기획서, 코드, 평가표, 실행 증거와 발표를 하나의 포트폴리오로 정리한다.

| 4–5주차 | 어떤 데이터와 외부 근거를 사용할 수 있는가 | 데이터 출처, 권한, 검색 기준선, 실패 사례 |
| 6–7주차 | 왜 이 기술 접근을 선택하는가 | 기술 대안 비교, 모델 적응 타당성, 평가 계획, 기획서 초안 |
| 8주차 | 이 기획은 구현·평가·운영 가능한가 | 기말 프로젝트 기획서 0.1 제출, 결정 기록, 후속 수정 계획 |

## 수업 일정 기준

- 매주 금요일을 기준으로 1주차는 2026년 9월 4일, 16주차는 12월 18일이다.
- 전 주차를 대면 수업 없이 온라인으로 운영하며, 별도 표기가 없는 주차는 정해진 시간의 실시간 온라인 강의다.
- 4주차인 9월 25일 추석과 6주차인 10월 9일 한글날은 휴강이 아니다. 정규 실시간 온라인 강의 대신 녹화 강의영상을 업로드하고 학습 범위·실습·산출물은 그대로 운영한다.
- 8주차에는 중간고사와 실시간 온라인 강의가 없다. 기말 프로젝트 기획서 0.1을 온라인으로 별도 제출하고 제출물 평가를 진행한다.

- 실시간 접속 정보, 녹화영상 위치·시청 기한과 제출 시각은 소속별 수업·과제 공지를 따른다.

## 교수 질의응답 운영

질의응답은 정답을 대신 제시하는 시간이 아니라 **가정과 증거의 연결을 검토하는 설계 리뷰**다.

1. 수강생은 질문 전에 현재 문서 버전과 확인받을 의사결정을 제시한다.
2. 교수는 문제, 데이터, 기술, 평가, 운영 위험 가운데 가장 큰 불확실성을 질문한다.
3. 수강생은 답변을 그대로 수용하는 대신 채택·보류·반박 중 하나를 결정하고 근거를 기록한다.
4. 수정본에는 변경 전후, 변경 이유, 추가한 증거와 남은 위험을 남긴다.
5. 질문 기록과 수정 이력은 기말 포트폴리오의 평가 근거가 된다.

권장 기록 단위:

| 항목 | 기록 내용 |
|---|---|
| 현재 버전 | 문서·코드·데이터의 버전 또는 커밋 |
| 질문 | 교수에게 확인할 한 가지 의사결정 |
| 근거 | 현재 판단을 뒷받침하는 실행·사용자·데이터 증거 |
| 피드백 | 질문을 통해 드러난 가정, 누락, 위험 |
| 학생 결정 | 채택·보류·반박과 그 이유 |
| 다음 수정 | 담당, 완료 조건, 다음 검토 시점 |

## 평가 원칙

아이디어의 화려함보다 다음 다섯 질문의 답과 근거를 확인한다.

1. 문제 정의: 대상 사용자와 지원할 의사결정이 구체적인가
2. 실행 가능성: 데이터, 기술, 일정과 역할의 범위가 현실적인가
3. 평가 가능성: 성공·실패·중단 조건을 비교 가능한 방식으로 정의했는가
4. 운영 가능성: 권한, 개인정보, 비용, 지연시간과 복구를 다루는가
5. 수정 가능성: 질의응답 이후 판단 변화와 근거를 추적할 수 있는가
