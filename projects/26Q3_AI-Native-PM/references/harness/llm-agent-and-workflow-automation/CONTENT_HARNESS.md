# 차성재 강의 콘텐츠 하네스

이 문서는 PPT를 한 번 예쁘게 만드는 규칙이 아니라, 강의 메시지가 버전이 바뀌어도 흔들리지 않게 관리하는 기준이다. 장표·노트북·코드·캡처를 고칠 때 모두 같은 질문을 사용한다.

Day 2~5의 8시간 성립 조건, 오프닝 결과 Demo, 240장 중복 Gate, Notebook·Codex·Claude Code 검증은 `COURSE_QUALITY_VALIDATION.md`를 함께 적용한다.

## 1. 커뮤니케이션 한 문장

> 8시간이 끝나면 처음 배우는 학습자도 **STT → LLM → Tool → LangGraph → Human Review → LangSmith** 흐름을 말로 설명하고, 무료·로컬 우선 환경에서 실패를 재현한 증거를 남길 수 있어야 한다.

강의의 중심은 특정 모델 사용법이 아니다. 실제 업무 Workflow를 **통제 가능하고, 중단 가능하고, 재실행 가능하고, 관측 가능하게 만드는 방법**이다.

## 2. 메시지 우선순위

### Level 0 · 하루 전체의 결론

- 모델은 바뀐다. 책임 경계·검증·복구·평가 증거는 제품에 남는다.
- 무료 실습은 ‘모든 도구가 공짜’라는 뜻이 아니다. 유료 서비스가 없어도 fixture·local·dry-run으로 핵심 계약을 학습할 수 있다는 뜻이다.
- Codex·Claude는 결과를 대신 책임지는 도구가 아니다. Spec → Diff → Test → Review를 빠르게 반복하는 Harness다.

### Level 1 · 여덟 차시의 역할

1. 문제정의: 오늘 만들 제품과 완료 증거를 정한다.
2. Tool Calling: 모델의 제안과 실제 실행 권한을 분리한다.
3. 한국어 PBL 데이터: 자연스러운 요약보다 사람·숫자·날짜·근거를 보존한다.
4. 환경·Git: 설치 성공이 아니라 다른 사람이 다시 실행할 수 있게 만든다.
5. Safe Loop: LLM을 붙이기 전에 validation·timeout·stop을 결정론적으로 통과한다.
6. 무료·Local LLM: provider가 바뀌어도 contract가 남는 adapter를 만든다.
7. LangGraph·HITL: 중단·승인·수정·거절·재개를 State와 event로 남긴다.
8. STT·LangSmith: trace를 쌓는 데서 끝내지 않고 READY/HOLD 배포 결정으로 닫는다.

### Level 2 · 차시 안의 진행 순서

각 차시는 아래 순서를 따르되, 같은 설명을 다른 형식으로 반복하지 않는다.

1. **질문**: 앞 차시에서 새로 생긴 문제를 한 문장으로 던진다.
2. **개념**: 이 차시가 소유한 용어와 판단 기준만 설명한다.
3. **근거 화면**: 공식 문서·실제 실행 화면에서 확인할 지점을 지정한다.
4. **코드**: 개념을 지키는 경계 한 줄을 찾는다.
5. **개인 활동**: Ideation·자료 수집·설계 워크숍·소프트웨어 실습 중 실제 행동을 정확히 부른다.
6. **Gate**: 앞 내용을 다시 말하지 않고, 처음 보는 상황에 적용해 판단한다.

### 금지

- 차시 시작 장표와 다음 장표가 같은 결론을 말하는 것
- ‘이 차시가 끝나면…’, ‘화면은 네 가지만…’ 같은 범용 제목을 모든 차시에서 복제하는 것
- 중간 checkpoint가 방금 설명한 문장을 그대로 질문으로 바꾸는 것
- STT·Human Approval·LangSmith의 구현 설명을 소유 차시보다 앞에서 완결해 버리는 것
- 결론·요약·정리 장표를 차시마다 두는 것

### 중간 Gate 작성법

- 재진술 질문: “Idempotency가 왜 필요한가?” → 사용하지 않는다.
- 적용 질문: “승인 뒤 같은 request_id가 다시 들어왔다. 발행할까, cached result를 돌려줄까?” → 사용한다.
- 정답은 speaker notes에 둔다. 화면에는 상황·선택·판단 근거만 둔다.

## 4. 메시지 소유권과 예고

- 오프닝은 전체 구조를 **예고**할 수 있지만 구현 원리를 설명하지 않는다.
- Tool Calling은 Human Approval을 ‘쓰기 권한 경계’로만 예고한다.
- 한국어 데이터 차시는 STT를 ‘입력 계약’으로만 다룬다.
- 환경 차시에서 Harness Engineering을 실제 폴더·Git·테스트 루프로 구체화한다.
- Safe Loop가 timeout·retry·stop의 1차 소유자다.
- LangGraph 차시가 interrupt·resume·HITL·idempotent publish의 1차 소유자다.
- 마지막 차시가 STT 품질·LangSmith trace·dataset·evaluation·release gate의 1차 소유자다.

정확한 범위와 산출물은 `DAY1_MESSAGE_MAP.json`을 단일 기준으로 사용한다.

## 5. 장표 역할 태그

장표를 추가할 때 아래 역할 중 하나를 선택한다. 역할을 설명할 수 없으면 추가하지 않는다.

- `PROMISE`: 학습 결과·운영 계약
- `QUESTION`: 다음 차시를 여는 긴장
- `TERM`: 초심자 용어 정의
- `CLAIM`: 한 장 한 주장
- `EVIDENCE`: 공식 문서·실제 화면
- `CODE_BOUNDARY`: 계약을 지키는 코드
- `IDEATION`: 문제·사용자·범위를 개인 notebook에서 구체화
- `DATA_COLLECTION`: 공개 자료·이용 조건·근거 구간을 수집
- `DESIGN_WORKSHOP`: State·Schema·정책을 실행 전 구조화
- `SOFTWARE_LAB`: 환경 세팅·코드 작성·명령 실행·테스트·배포
- `FAILURE_CASE`: 의도적 실패와 복구
- `APPLICATION_GATE`: 새 상황에 적용
- `FINAL_SYNTHESIS`: 하루 마지막 회수

같은 메시지 ID에 `CLAIM`과 `FINAL_SYNTHESIS`를 제외한 두 개 이상의 설명 장표를 연결하지 않는다. 화면·코드·개인 활동은 같은 주장을 되풀이하는 것이 아니라 서로 다른 증거여야 한다.

## 활동 명칭 분류 기준

`실습`은 손으로 무언가 적는 모든 시간의 통칭이 아니다. 아래 기준으로 제목·시간표·강사용 교안을 동일하게 분류한다.

| 명칭 | 사용 조건 | 완료 증거 예시 |
|---|---|---|
| Ideation | 문제·사용자·입력·금지 행동을 정함 | 문제 정의 한 문장, PBL canvas |
| 자료 수집 | 공개 데이터·공식 문서·이용 조건·근거를 찾음 | URL, Dataset Card, evidence ID |
| 설계 워크숍 | Schema·State·권한·Retry 정책을 실행 전 구조화 | schema 표, graph sketch, policy matrix |
| 개발환경 세팅 실습 | Python·VS Code·Git·kernel을 직접 설치·선택·검증 | version, interpreter path, branch |
| 소프트웨어 실습 | 코드를 작성·수정하고 명령을 실행해 결과를 저장 | `.py`·`.ipynb`, pytest, state JSON, trace |
| 실행 확인 | 이미 만든 소프트웨어의 상태·결과·오류를 비교 | READY/HOLD, diff, error code |

- `소프트웨어 실습` 장표에는 최소 하나의 실제 파일명·명령·실행 결과가 있어야 한다.
- 생각만 적는 활동에 `실습`이라는 이름을 붙이지 않는다.
- 공식 홈페이지를 읽는 것만으로 소프트웨어 실습을 대체하지 않는다. 공식 문서는 개념 근거이며, 수업 산출물은 실행 코드·테스트·결과 파일이다.
- LangChain·LangGraph·LangSmith 차시는 `개념 → 실제 코드 → 정상/실패 실행 → 상태/trace 저장 → 브라우저 결과 확인` 순서를 기본으로 한다.
- 4~8차시는 서로 떨어진 Demo가 아니라 `04 notebook 환경 진단 → Ollama Tool Call → LCEL provider 교체 → 07 notebook StateGraph 승인 → STT·trace·READY/HOLD`로 입력과 결과 계약이 이어져야 한다.
- Ollama를 필수 설치 성공으로 표현하지 않는다. `CLI·서버·모델` 상태와 실제 사용 provider, fallback 이유를 각각 화면과 결과에 남긴다.

## 강의 작성을 위한 Harness Engineering 기준

아래 항목은 학습자에게 가르칠 본문이 아니라, 강의 자료를 만드는 제작자가 지킬 내부 표준이다. `개발자 발표는 화면을 크게, 문장은 짧게`와 같은 제작 지침을 별도 강의 장표로 만들지 않는다.

- **명사형 제목**: 장표 제목은 핵심 개념·기능·결과를 짧은 명사형으로 쓴다. `합니다`, `됩니다`, `있습니다`로 끝나는 문장은 제목에 두지 않는다.
- **표지 부제**: 표지의 부제는 핵심 기술·과업·산출물의 키워드 조합으로 쓴다. 설명 문장은 일반 장표의 부제·본문·speaker notes로 내린다.
- **한 장 한 역할**: 제목만 읽어도 개념·비교·실행·검증 중 어떤 내용을 다루는지 구분되게 한다.
- **실제 화면 우선**: 서비스를 설명할 때는 메뉴 위치·실행 명령·성공 신호가 보이는 실제 캡처를 사용한다.
- **문장은 짧게**: 배경 설명은 speaker notes에 두고 화면에는 주장·근거·행동만 남긴다.
- **출처는 notes에**: 외부 이미지와 비상식적 주장은 `[Sources]` 블록으로 추적한다.
- **제작 규칙은 화면 밖에**: 장표 작성법·분량 조절법·디자인 참고 문장은 콘텐츠가 아니라 이 문서에서 관리한다.
- **반복 구조는 표로 통합**: 같은 레이아웃이 3장 이상 이어지면 비교표·의사결정표·한 장짜리 용어표로 합칠 수 있는지 먼저 본다.
- **같은 위계는 같은 색상**: 표의 열들이 같은 역할이라면 한 열만 accent 색으로 강조하지 않는다. 정말 중요한 경고·결정·상태에만 파란색을 사용한다.
- **순서만으로 강조하지 않기**: 목록·표·프로세스의 마지막 항목이라는 이유만으로 헤더·번호·구분선을 파란색으로 바꾸지 않는다. 같은 역할의 항목은 검정색으로 통일한다.
- **PDF 호환 글꼴**: 본문은 변환 PC에 실제 설치된 일반 고딕체를 쓴다. 현재 강사 Mac의 인쇄 경로는 `AppleGothic`, Windows 편집본은 `맑은 고딕`·`굴림`을 우선한다. 이름이 비슷한 글꼴로 자동 대체됐다는 이유만으로 통과시키지 않고, 최종 PDF에서 해당 글꼴이 embed됐는지와 한글 glyph를 전 페이지 렌더링으로 확인한다. 코드 글꼴은 `Menlo`처럼 실제 설치·embed가 확인된 경우에만 사용한다.
- **장표 수보다 학습 흐름**: 목표 장수를 채우기 위해 같은 메시지를 분할하지 않는다. 강의 시간은 실습·오류 복구·반례·Q&A로 확장한다.
- **도구는 맥락과 함께**: 도구명만 나열하지 않고 도메인·역할·선정 이유·유사 대안과의 차이를 함께 설명한다.
- **선택 도구와 필수 도구를 분리**: VS Code·Git·fixture처럼 모두가 따라야 할 경로와 Codex·Claude·Local LLM처럼 환경에 따라 선택할 경로를 구분한다.
- **화면은 크게**: 실제 캡처는 조작 위치와 성공 신호를 읽을 수 있는 크기로 배치하고, 설명 텍스트가 화면을 밀어내지 않게 한다.
- **실습 명칭 제한**: `소프트웨어 실습`은 IDE·Notebook·Terminal·Codex에서 실제 코드를 생성·수정·실행하고 test 또는 결과 파일을 저장할 때만 사용한다.
- **참고 화면 분리**: 홈페이지·공식 문서·서비스 화면을 보는 구간은 `참고 화면` 또는 `자료 확인`으로 표시한다. 웹 화면 확인만으로 실습을 구성하지 않는다.
- **표준 시간 블록**: 2~5일차는 09:00-11:30 1~3차시, 11:30-13:00 쉬는 시간·점심시간, 13:00-14:40 4~5차시, 14:40-15:00 쉬는 시간, 15:00-17:30 6~8차시, 17:30-18:00 쉬는 시간·Q&A로 운영한다. 1일차의 14:00 점심은 해당 날만의 예외로 분리한다.

### 학생용 Copy 기준

- 제목은 `2~8단어의 명사형`을 기본값으로 한다. 차시명·파일명·`필요성`, `학습 결과`, `정리`를 기계적으로 결합하지 않는다.
- 제목은 그 페이지가 새로 추가하는 판단·구조·코드·결과를 표시한다. 제목과 부제, 제목과 첫 본문이 같은 결론을 반복하면 하나를 삭제한다.
- 동일한 Main Title은 시간표·차시 표지·마지막 Q&A를 제외하고 반복하지 않는다. `실행 명령`, `오류 복구`, `Codex 대화`처럼 범용 제목이 필요하면 `Input Adapter Test 명령`, `MCP Policy 오류 복구`처럼 대상이 드러나는 이름을 쓴다.
- 파일명은 Main Title이 아니라 `FILE` Label이나 표의 경로 열에 둔다. 파일 자체가 학습 대상일 때만 제목에 사용한다.
- Code Identifier는 처음 등장할 때 학생 언어를 먼저 쓰고 괄호로 병기한다. 예: `외부 저장·발송(External Action)`, `실행 이력(Execution Log)`.
- 다음 단어는 맥락 없는 단독 Label로 사용하지 않는다.

| 피할 표현 | 학생용 표현 |
|---|---|
| 책임 | `Role`, `Owner`, 담당 범위 |
| 정상 | `Expected Output`, `Happy Path`, 실행 완료 |
| 경계 | `Boundary Test`, 제한 조건, 예상 오류 |
| 외부 쓰기 | 외부 서비스 저장·게시·발송, `External Action` |
| 기록 | 실행 이력, `Execution Log`, `Audit Log` |
| 증거 | 원문 근거, Test 결과, `Evidence ID` |
| 사람 검증 | `Human Review`, 사용자 승인 |
| 결과 계약 | 결과 형식, `Result Schema` |

| 차시 표지 | 40pt | 44~48pt |
| 일반 제목 | 34pt | 36~40pt |
| 본문 | 18pt | 20~24pt |
| 표 Cell | 17pt | 18~20pt |
| Code | 15pt | 16~18pt |
| Footer | 9pt | 10pt |

- `shrinkText`로 문제를 숨기지 않는다. 글씨를 줄이기 전에 문장 축약, 표 통합, 코드 분할을 적용한다.
- 숫자 `01·02·03` 같은 장식 Label도 실제 16pt 이상으로 만들거나 의미 있는 Type Label로 바꾼다.
- 표 한 Cell의 개행은 의미 단위로 직접 지정한다. Path·명령·완료 조건을 한 줄에 억지로 압축하지 않는다.
- Screenshot은 캡처 내부의 메뉴·상태·결과가 보일 때만 사용한다. 읽히지 않는 전체 화면은 확대본으로 대체한다.

### PPT 단독 재실행 기준

각 차시는 아래 역할을 한 번씩만 가진다. 같은 설명을 늘리는 대신 실제 실행의 앞뒤를 완성한다.

1. `준비 파일`: 읽기·실행·수정·Test의 Role과 정확한 경로
2. `핵심 개념`: 이 차시가 처음 소유하는 용어와 선택 기준
3. `강사 Demo`: Input·Command·Expected Output·Expected Error
4. `소프트웨어 실습`: 실행 가능한 Notebook Cell 또는 Terminal 명령
5. `Codex Task`: Goal·Allowed·Test·Do not
6. `실행 확인`: 결과 File·Error Code·External Action 여부
7. `재실행`: 준비 파일부터 결과 확인까지 한 장의 순서

- 학생용 장표의 Code는 생략 부호로 끝내지 않는다. 전체 Code가 길면 실행 Cell의 경로와 수정할 줄을 명확히 표시하고, PPT에는 완전한 명령을 둔다.
- Speaker Notes는 강사의 발화·시간·심화 반례를 담는다. 학생이 실행에 필요한 정보는 Notes로 숨기지 않는다.
- 50분은 `핵심 이론 13분 → 강사 Demo 8분 → Notebook·Terminal 14분 → Codex Task 8분 → Test·복구 7분`을 기본값으로 한다. 장표 수가 아니라 이 행동 시간이 성립하는지 검증한다.
- 온라인 기본 운영은 개인 Follow-along이다. 짝·발표·화면 공유를 전제로 한 단계는 학생용 장표에 넣지 않는다.

### 화면에 보여줄 것과 내부에 남길 것

| 구분 | PPT 화면에 보여줄 내용 | Harness MD·speaker notes에 남길 내용 |
|---|---|---|
| 학습 메시지 | 개념·판단 기준·업무 맥락·왜 중요한가 | 메시지 소유권·장표 역할 태그·작성 의도 |
| 개인 활동 | 활동 종류·입력·행동·완료 신호·실패 시 복구 | talk track·소요 시간 추정·진행 속도 조절법 |
| 도구 | 도메인·역할·선정 이유·유사 대안과의 차이 | 캡처 제작 지시·레이아웃 규칙·이미지 후보 |
| 검증 | test 결과·schema·승인 조건·READY/HOLD 기준 | 중복률·밀도·장표 수·검수 메모 |
| 운영 안내 | 실제 시간표·점심·쉬는 시간·학습자 행동 | 제작자용 일정 계산·강의 운영 가설 |

- 화면의 모든 문장은 학습자가 **이해하거나, 판단하거나, 실행하거나, 완료를 검증하는 데** 직접 도움을 줘야 한다.
- `KEY POINTS`, `CORE IDEA`, `FOLLOW ALONG`, `SCREEN ROUTE` 같은 장표 역할 태그는 제작·검수용 메타데이터다. 학습자 화면에는 한국어 행동 라벨로 바꾸거나, 없어도 의미가 통하면 표시하지 않는다.
- `개발자 발표는 화면을 크게, 문장은 짧게`, 장표 밀도, 장수 목표, 디자인 변주 같은 지시는 PPT 본문에 넣지 않는다.
- 강사의 말하기 메모·심화 반례·시간 여유분은 speaker notes나 별도 운영 문서에 둔다. 학습자에게 행동을 요구할 때만 화면에 올린다.
- 위 기준을 통과하지 못한 문장은 삭제하거나 notes·Harness MD로 이동한다. 장수를 유지하기 위한 대체 장표는 만들지 않는다.

### 온라인 개인 활동 기본값

- 이 과정의 기본 운영은 **온라인·개인 활동·강사 따라하기**다.
- 짝 활동, 조별 토론, 돌아가며 발표, 화면 공유를 기본 활동으로 넣지 않는다.
- 재직 여부·회사 업무·구직 상황·개인 프로젝트 주제를 채팅창이나 전체 화면에 공개하도록 요구하지 않는다.
- 학습 결과는 기본적으로 각자의 notebook·로컬 파일·Git 저장소에 남긴다. 제출이나 공유가 꼭 필요할 때만 별도로 안내한다.
- 질문은 `첫 오류 문장 + 직전 행동 + 실행 환경 + 기대 결과`를 채팅창에 남기는 방식으로 받는다.
- Gate는 개인이 화면을 보며 판단하고, 강사가 대표 사례를 해설하는 방식으로 운영한다. 수강생 발표는 요구하지 않는다.
- 활동 문구는 `피어 리뷰`, `lane`, `발표 목표` 같은 운영 용어보다 `지금 할 일`, `완료 화면`, `막혔을 때 행동`처럼 바로 이해되는 표현을 우선한다.

9. 웹사이트 확인을 소프트웨어 실습으로 잘못 분류하지 않았는가?

## 8. 변경 기록 원칙

- PPT 파일을 덮어쓰지 않는다. 의미 있는 개정마다 새 suffix를 붙인다.
- 메시지 변경은 먼저 `DAY1_MESSAGE_MAP.json`에 반영한 뒤 장표를 고친다.
- 반복을 의도적으로 허용하면 허용 목록에 문구·범위·이유를 함께 남긴다.
- 장표 수를 유지해야 할 때 중복 장표를 삭제만 하지 않는다. 반례·새 사례·판단 Gate·실제 화면 증거로 전환한다.
- 모델이 만든 문구는 강사가 실제로 말할 수 있는 문장인지 소리 내어 읽고 확정한다.
