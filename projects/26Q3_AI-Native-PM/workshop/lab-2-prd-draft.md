### 0-1. 머니핏 완성 예시 (그대로 복사해 §B Step 2 프롬프트의 [자료]에 붙입니다)

```text
1. 서비스명: 머니핏(MoneyFit) — 가상 회사 핀트리(FinTree)의 마이데이터 기반 2030 직장인 자산관리 코칭 앱. 핀트리는 시리즈 A 단계 핀테크 스타트업으로 본인신용정보관리업(마이데이터) 허가를 취득한 것으로 가정한다 [가정].

2. 타겟 유저: 25–35세 급여 소득 직장인. 은행 계좌 3개 이상·카드 2장 이상을 나눠 쓰고 있어 월 소비를 한눈에 보지 못한다 [가정]. 저축 목표를 세워도 3개월 안에 절반 이상이 앱 사용을 멈춘다 [가정]. 금융 지식은 보통, 투자보다 "새는 돈 막기"에 관심이 크다 [가정].

3. 핵심 문제: "내 돈이 어디로 가는지 모른다." 월말에 여러 앱을 오가며 소비를 파악하는 데 평균 40분이 걸리고 [가정], 계좌를 연동한 사용자 4명 중 1명은 저축 목표 설정 전에 이탈하고, 목표를 세운 사용자 10명 중 3명은 첫 저축까지 가지 못한다 [가정]. 원인 후보는 파악 비용(시간)과 실행 실패(자동화 부재) 두 가지 [확인 필요].

4. AI 활용점: ① 연동 거래 내역 자동 카테고리 분류와 월간 요약 ② 소비 패턴 인사이트 문구(예: "이번 달 배달비가 지난 3개월 평균보다 높아요") ③ 목표 기준 개인화 코칭 메시지 ④ 목표 달성 시뮬레이션 설명 — 투자 권유가 아닌 정보 제공 범위(컴플라이언스 확인 필요) ⑤ 고객 문의 1차 응대.

5. 성공 기준(모두 [가정] — Baseline은 8월 퍼널 잠정치이며 Session 3 데이터 분석(14:30)에서 같은 가상 데이터로 재계산한다):
   - 핵심 ① 첫 저축 목표 설정율(계좌 연동 사용자 대비): Baseline 72.5% → Target 80% · 측정 이벤트 set_goal
   - 핵심 ② 첫 저축 실행율(목표 설정자 대비): Baseline 71.0% → Target 78% · 측정 이벤트 first_saving
   - 보조 ③ 30일 활성(가입자 대비): Baseline 30.0% → Target 35% · 측정 이벤트 d30_active
   - 확인 시점: 출시 후 8주 [가정]
```

## A. 미니 실습 (12:57–13:05 · 8분) — 경쟁 서비스 벤치마킹 표

| 항목 | 내용 |
|------|------|
| 목표 | 표 뼈대는 AI가, '존재 확인'과 '시사점'은 사람이 채우는 분업을 체험한다 |
| 시간 | 8분 = 입력 1 · 생성 대기 1.5 · 결과 확인 1.5 · (시간 되면) 사이트 확인 2 · 재요청+대기 2 |
| 산출물 | 벤치마킹 표 1개(열 9개 · '존재 확인' 열 전부 "미확인" · 시사점 열) — 시간 되면 '존재 확인' 1건을 "확인(출처 URL, 확인일)"로 갱신 |
| 준비물 | 무료 계정 1개 · 비교할 서비스 이름 3개(본인이 아는 것을 직접 입력. 모르면 프롬프트 안의 대체 문장 사용) |

> **왜 '존재 확인' 열인가**: AI가 경쟁사 기능을 말하면 그것은 학습 데이터의 '기억'이지 확인된 사실이 아닙니다. 없는 기능을 있다고 쓰는 것은 금융에서 위험한 환각 4곳 중 하나입니다. 그래서 표에 '존재 확인' 열을 박아 두고 사람이 채웁니다. 이 문서의 예시 표는 실제 서비스를 평가하지 않기 위해 **가상 A사·B사·C사**로 채웠습니다.

### Step 1 입력 — 아래 전체를 복사해 `[서비스 1/2/3]`만 바꿔 붙여넣기

```text
[역할] 당신은 핀테크 기획팀의 벤치마킹 담당자입니다. 확인되지 않은 사실을 확인된 것처럼 쓰지 않습니다.

[목적] 가상 서비스 '머니핏(MoneyFit)'(마이데이터 기반 2030 직장인 자산관리 코칭)의 기획에 참고할 경쟁·유사 서비스 벤치마킹 표를 만듭니다. 목적은 '우리에게 시사점'을 얻는 것이며, 특정 서비스의 우열 평가가 아닙니다.

[독자] 기획자 본인과 팀. 이 표를 스프레드시트로 옮겨 계속 갱신할 예정입니다.

[자료] 비교 대상 서비스: [서비스 1], [서비스 2], [서비스 3]
(서비스 이름을 모르면 위 줄을 다음 문장으로 바꿉니다: "국내 2030 직장인 대상 자산관리·가계부·마이데이터 서비스 후보 3개를 제안하되, 모두 존재 확인=미확인으로 표시")
당신이 학습 데이터에서 기억하는 정보는 '기억'일 뿐 확인된 사실이 아닙니다. 그 전제로 작성합니다.

[형식] Markdown 표 1개. 행 = 서비스 3개 + 마지막 행 '머니핏(우리, 목표)'.
열 = 서비스 | 존재 확인 | 타겟 | 핵심 기능 | 가격·수익 모델 | UX 강점 | AI 활용 | 규제 대응(마이데이터 허가 등) | 우리에게 시사점
- '존재 확인' 열은 모두 "미확인"으로 채웁니다. 사람이 확인한 뒤 "확인(출처 URL, 확인일)"로 바꿀 수 있게 둡니다.
- 확인되지 않은 셀에는 [확인 필요]를, 추정에는 [가정]을 붙입니다. 빈 셀은 '—'로 채웁니다.
- 마지막 열 '우리에게 시사점'은 행마다 한 문장.
- 표 아래에 "직접 확인해야 할 것 3개"를 목록으로 쓰고, 각 항목에 어디서 확인하는지(공식 홈페이지·앱스토어 설명·금융감독원 전자공시시스템(DART)·보도자료)를 붙입니다.

[검증]
- 자료에 없는 숫자나 사실은 만들지 말고 [확인 필요]로 표시합니다(이용자 수·거래액·요금 포함).
- 서비스가 실제로 존재하는지 확신할 수 없으면 존재 확인 열에 "미확인(존재 여부 불명)"이라고 씁니다.
- 특정 서비스를 비판·평가하는 표현 대신 "공개된 기능 기준"으로만 씁니다.
- 법률 판단 문장은 쓰지 않고, 규제 대응 열은 "확인 질문" 형태로 씁니다.
```

### Step 2 결과 확인 (3개)

- [ ] '존재 확인' 열이 **전부 "미확인"** 인가 — 하나라도 "확인"이라 쓰여 있으면 AI가 확인하지 않은 것을 확인했다고 쓴 것 → 오류
- [ ] 확인되지 않은 셀에 `[확인 필요]`, 추정에 `[가정]`이 붙었나
- [ ] 마지막 열 '우리에게 시사점'이 행마다 한 문장 있나

### Step 3 한 번 수정(시간 되면) — 1개만 내 손으로 확인하고 표에 반영

시간이 남을 때만 합니다. 서비스 1개의 **공식 홈페이지 또는 앱스토어 설명**을 열어(회사 노트북에서 안 열리면 휴대폰으로, 그것도 어려우면 건너뜁니다) ① 존재 ② 핵심 기능 1개를 확인한 뒤, 아래 문장을 채워 같은 대화에 붙입니다.

```text
[서비스 1]은 공식 페이지([URL])에서 존재와 '[확인한 기능명]'을 확인했습니다(확인일 2026-09-19). 존재 확인 열을 "확인([URL], 2026-09-19)"로 갱신하고, 확인하지 않은 다른 셀의 [확인 필요]는 그대로 유지해 주세요. 표만 다시 출력해 주세요.
```

### 성공 기준

열 9개가 있고 · '존재 확인' 열이 전부 "미확인"이고 · 시사점 열이 행마다 있고 · `[확인 필요]`가 유지된다. 존재 확인 1건 갱신은 시간이 됐을 때의 추가 성공. **결과가 옆사람과 달라도 정상 — 열 구성·`[확인 필요]` 표기·시사점 열만 함께 확인.**

### Step 3 리뷰 (13:40–13:50) — 3관점 AI 리뷰 (반드시 **새 대화**)

| Step 3에 무엇을 붙일지 헷갈림(원본 vs 수정 조각) | 처음 나온 PRD 전체(원본)만 붙인다. Step 2 재요청으로 받은 조각은 붙이지 않는다 |
| 결과를 메모장에 붙이니 #·\| 기호가 보임 | 깨진 것이 아니라 마크다운(Markdown) 형식. 채팅 화면의 복사 버튼으로 Word·노션에 붙이면 표로 들어간다 |
| 리뷰가 칭찬만 함 | Step 3의 재요청 문장("칭찬은 빼고 가장 약한 3곳만, PRD 문장 인용") |
| 시간 부족(Step 3 보완 못 함) | 보완을 Step 4 2-Pager 프롬프트에 합친다: 첫 줄에 "아래 리뷰의 약점 3개를 반영하여" + '가장 약한 3곳' 표 첨부 |
| 시간 부족(Step 4) | "첫 5줄 결론만 먼저 써 주세요" — 첫 5줄만 있어도 산출물로 인정 |

## E. 월요일에 회사에서 쓸 때

1. **복원**: 치환한 `[가정]` 값을 실제 값으로 바꾸는 작업은 **회사가 승인한 환경**에서만. 외부 무료 계정에 실제 지표·고객 데이터를 넣지 않습니다.
2. **컴플라이언스**: PRD §7의 질문 목록을 그대로 준법감시·컴플라이언스 담당에게 보냅니다. 답이 오기 전까지 상태는 `[확인 필요]`. AI가 쓴 법령 조항 번호·해석은 인용하지 않습니다.
3. **사람이 결정**: P0/P1 · 지표 Target · 요청 사항은 회사 사정을 아는 사람이 정합니다. AI는 후보와 근거까지.
4. **회사 양식이 다를 때**: Step 2 프롬프트 `[형식]`의 섹션 이름만 회사 양식의 섹션 제목으로 바꿉니다(양식 파일 자체는 붙이지 않음). 두괄식·지표 3종·규제 질문 목록·마지막 요청 문장은 유지를 권합니다.
5. **대외 제안서가 필요할 때** — 같은 PRD, 바뀌는 건 독자와 목적. 초안 대화에 붙입니다.

```text
같은 내용을 [고객사/파트너/심사위원]에게 보내는 대외 제안서로 바꿔 주세요. 독자는 [독자], 목적은 [채택/계약/선정]입니다. 내부 비용·인력·확정되지 않은 지표·내부 리스크는 제외하고, 고객이 얻는 이익 → 우리의 해법 → 도입 절차 → 요청 사항 순서로 A4 1페이지로 써 주세요. 규제는 확인된 준수 사항만 쓰고, 확인되지 않은 것은 [확인 필요] 표시를 유지하거나 제외합니다. 자료에 없는 숫자나 사실은 만들지 말고 [확인 필요]로 표시하세요.
```

6. **프롬프트 저장**: 오늘 쓴 프롬프트 5개(벤치마킹·리서치 브리프·PRD 초안·3관점 리뷰·2-Pager)를 개인 템플릿 폴더에 v1으로 저장하고, 다음에 고친 부분을 v2로 남깁니다. 리뷰에서 매번 약하다고 나온 항목을 다음 PRD 프롬프트의 `[형식]`·`[검증]`에 미리 넣으면 첫 초안 품질이 올라갑니다 — "프롬프트는 문서다".

## 용어

| 용어 | 뜻(한 줄) |
|------|----------|
| 제품 요구사항 정의서(Product Requirements Document, PRD) | 무엇을 왜 만드는지 정의한 기획서. 팀의 단일 진실 원천(Single Source of Truth, SSOT) |
| 두괄식(Bottom Line Up Front, BLUF) | 결론을 문서·섹션 맨 앞에 쓰는 방식 |
| 마크다운(Markdown) | 제목·표를 `#`·`\|` 기호로 쓰는 문서 형식. 채팅 화면에서는 표로 보이고, 메모 앱에 붙이면 기호가 보이는 것이 정상. Word로 옮길 땐 채팅 화면의 복사 버튼 사용 |
| 2-Pager | 리더십 승인용 2페이지 요약. "왜 이걸 하는가"에 답한다(오늘은 1페이지로 압축) |
| P0 / P1 | 최소 출시 범위(Priority 0) / 다음 단계 기능(Priority 1) |
| Baseline → Target → 측정 이벤트 | 현재값 → 목표값 → 그 값을 계산하는 로그(이벤트) 이름(영문 소문자와 밑줄, 예: set_goal). 지표 3종 세트 |
| 마이데이터(본인신용정보관리업) | 개인이 자신의 신용정보를 한곳에 모아 관리하도록 하는 신용정보법상 허가업 `[확인 필요]` |
| 전송요구권 | 개인이 자기 정보를 다른 사업자에게 보내달라고 요구할 수 있는 권리(신용정보법·개인정보보호법 관련) `[확인 필요]` |
| 가명처리 | 개인을 알아볼 수 없도록 일부 정보를 삭제·대체하는 처리(개인정보보호법·신용정보법상 개념) `[확인 필요]` |
| 엔지니어링 매니저(Engineering Manager, EM) | 개발 리소스·일정·실현 가능성을 판단하는 개발 리드 |
| 동조 편향(sycophancy) | AI가 대화 상대(또는 자기 이전 답)에 맞춰 동의하는 쪽으로 기우는 경향 → 리뷰는 새 대화에서 |
| 1차 자료 / 2차 자료 | 숫자를 만든 곳(기관 통계·공시·보도자료) / 그 숫자를 옮겨 쓴 곳(기사·리포트) |
