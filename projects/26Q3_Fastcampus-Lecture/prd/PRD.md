## §2. Executive Summary

직장인 10명 중 8명은 매일 "오늘 점심 뭐 먹지?"를 고민하며, 평균 12분을 메뉴 결정에 소비한다. **오늘의 점심 메이트**는 사용자의 기분, 날씨, 예산, 식이 선호를 입력받아 AI가 맞춤 메뉴와 근처 식당을 추천하는 모바일 웹 서비스다. MVP 출시 후 3개월 내 추천 수락률 60%, 주간 재사용률 3회 이상을 목표로 한다.

## §3. Problem Definition

| 문제 ID | 문제 설명 | 영향 (정량) | 근거 자료 | 해결 방향 |
|---------|----------|-----------|----------|----------|
| P1 | 매일 반복되는 점심 메뉴 결정 피로감 | 직장인 1인당 연간 50시간 소비 (12분 × 250일) | 직장인 설문조사 (N=500) | AI 맞춤 추천으로 결정 시간을 2분 이내로 단축 |
| P2 | 같은 메뉴만 반복하게 되는 선택 편향 | 직장인 65%가 주 5일 중 3일 이상 같은 메뉴 반복 | 점심 앱 사용 로그 분석 | 다양성 알고리즘 적용으로 새로운 메뉴 발견율 증가 |
| P3 | 동료와 점심 메뉴 합의의 어려움 | 3인 이상 그룹의 평균 합의 시간 18분 | 사내 설문 (N=200) | 그룹 선호도 교집합 기반 추천 |

### AS-IS (현재 상태)

1. 점심시간 30분 전부터 "뭐 먹지?" 고민 시작
2. 네이버 지도 / 배달앱을 열어 주변 식당 탐색 (정보 과부하)
3. 동료에게 물어봐도 "아무거나"라는 답변
4. 결국 어제와 같은 식당, 같은 메뉴 선택
5. 점심 만족도 저하 → 오후 업무 집중도 하락

## §4. Solution Proposed

### 핵심 가설

> "만약 사용자의 기분·날씨·예산·식이 선호를 기반으로 AI가 개인화된 점심 메뉴를 추천하면, 메뉴 결정 시간이 12분에서 2분 이내로 단축되고, 식사 만족도가 30% 이상 향상될 것이다"

### AS-IS → TO-BE

| 구분 | AS-IS | TO-BE |
|------|-------|-------|
| 메뉴 결정 시간 | 평균 12분 | 2분 이내 |
| 메뉴 다양성 | 주 3일 이상 동일 메뉴 | 주 5일 모두 다른 메뉴 가능 |
| 결정 방식 | 검색 → 스크롤 → 고민 → 포기 → 익숙한 곳 | 3가지 입력 → AI 추천 → 바로 출발 |
| 그룹 합의 | 카톡에서 30분 논쟁 | 그룹 선호도 매칭 3분 내 합의 |

### 분기별 로드맵

| 분기 | 주요 기능 |
|------|----------|
| Q3 2026 (MVP) | 개인 추천 (기분/날씨/예산 기반), 모바일 웹 |
| Q4 2026 | 그룹 추천, 식사 이력 학습, 식당 리뷰 연동 |
| Q1 2027 | 식당 예약 연동, 프리미엄 구독 모델 |

## §6. Scope

### In Scope (MVP)

- 개인 점심 추천: 기분(5가지) + 예산(3단계) + 선호 카테고리 입력 → AI 메뉴 3개 추천
- 위치 기반 식당 매칭: 현재 위치 반경 500m 내 식당 연결
- 추천 결과 카드: 메뉴명, 식당명, 거리, 예상 가격, 한줄 추천 이유
- 추천 수락/거절 피드백 (학습 데이터 수집)
- 모바일 웹 (반응형)

### Out of Scope

- 식당 예약/주문/결제 기능
- 식당 파트너십/광고 모델
- 네이티브 앱 (iOS/Android)
- 배달 연동
- 그룹 추천 (Q4 이후)

### Future Scope

- 그룹 선호도 매칭 (Q4 2026)
- 식사 이력 기반 개인화 고도화 (Q4 2026)
- 식당 예약 연동 (Q1 2027)

## §11. Success Metrics (KPI)

### North Star Metric

**주간 추천 수락률** — 사용자가 AI 추천을 수락하고 실제로 해당 식당을 방문한 비율

### Core Metrics

| 지표 | 정의 | Baseline | Target (3개월) | 측정 방법 |
|------|------|----------|---------------|----------|
| 추천 수락률 | 추천 결과 중 "수락" 클릭 비율 | 0% (신규) | 60% | 클릭 이벤트 추적 |
| 주간 재사용률 | 주 3회 이상 사용하는 유저 비율 | 0% | 40% | WAU/MAU 분석 |
| 메뉴 결정 시간 | 앱 오픈 → 수락까지 소요 시간 | 12분 (기존 방식) | 2분 이내 | 세션 타임스탬프 |
| NPS | 순추천지수 | 해당없음 | 40+ | 인앱 설문 (월 1회) |

### Release Gate

| 단계 | 통과 기준 | 미달 시 액션 |
|------|----------|-------------|
| 내부 테스트 (1주) | 추천 수락률 40% 이상 | 추천 알고리즘 튜닝 |
| 베타 (2주, 100명) | 추천 수락률 50%, 재사용률 30% | 페르소나별 추천 로직 분리 |
| 정식 오픈 | 추천 수락률 60%, NPS 40+ | 확산 중단 후 개선 |

## §12. AI Model & Technical Assumptions

### 모델 선택

| 항목 | 내용 |
|------|------|
| 추천 엔진 | Claude 3.5 Haiku (빠른 응답 + 저비용) |
| 입력 | 기분(enum) + 예산(enum) + 위치(좌표) + 식이제한(optional) |
| 출력 | 메뉴 3개 (JSON: 메뉴명, 카테고리, 추천이유, 예상가격) |
| 응답 시간 | p95 < 2초 |
| 토큰 비용 | 요청당 ~500 토큰 (입력 200 + 출력 300), 월 10만 요청 기준 약 $15 |

### 프롬프트 전략

```
시스템: 당신은 점심 메뉴 추천 전문가입니다.
사용자의 기분, 예산, 위치 정보를 바탕으로 최적의 점심 메뉴 3개를 추천합니다.

규칙:
1. 추천 이유를 한 문장으로 설명할 것
2. 예산 범위를 초과하지 않을 것
3. 같은 카테고리를 2개 이상 추천하지 않을 것
4. 날씨/기분에 맞는 음식을 우선할 것
```

### Fallback 전략

| 상황 | 대응 |
|------|------|
| API 응답 지연 (>3초) | 사전 캐싱된 인기 메뉴 Top 3 표시 |
| API 오류 | "오늘의 인기 메뉴" 정적 리스트로 대체 |
| 추천 결과 0건 | 예산/거리 범위를 자동 확장 후 재시도 |
