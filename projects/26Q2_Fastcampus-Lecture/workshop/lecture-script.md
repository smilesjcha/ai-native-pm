## Section 1: 오프닝 — 왜 지금 이 자리에 (5분)

> **슬라이드 1~5 / 18:10~18:15**

### 🎤 오프닝 멘트

> "안녕하세요, 반갑습니다. 오늘 이 자리에 오신 이유가 뭘까요? 아마 'AI'와 'PM'이라는 두 키워드가 만나는 접점에 대한 호기심이 아닐까 합니다."

### [슬라이드 3] 질문 던지기

**"2024년 대비 2026년, PM 채용 공고에서 가장 많이 추가된 키워드는?"**

- 손 들기 유도: "AI? 프로토타이핑? 데이터?"
- 정답 공개: **AI + Prototyping**
  - 2024년: PM 채용 공고 중 AI 언급 23%
  - 2026년: PM 채용 공고 중 AI 언급 67% (약 3배 증가)
  - 특히 "프로토타이핑 경험" 필수/우대 조건이 급증

### [슬라이드 4] 트렌드 차트

- PM 채용 키워드 변화 (2024 vs 2026) 시각화
- AI, Prototyping, Data Literacy 3개 키워드 증가 추세

### [슬라이드 5] 핵심 메시지

> **"AI가 PM을 대체하는 게 아닙니다. AI를 쓰는 PM이, 안 쓰는 PM을 대체합니다."**

- 포인트: AI는 도구다. 도구를 잘 쓰는 사람이 이긴다.
- 오늘 목표: **여러분이 직접 AI로 PRD를 쓰고, 프로토타입을 만들어 가실 겁니다.**

## Section 2: PM의 본질과 역할 변화 (10분)

> **슬라이드 6~9 / 18:15~18:25**

### [슬라이드 6] PM만이 할 수 있는 고유한 역할

> "개발자도 PRD를 쓸 수 있고, AI가 코드도 만들어주는 시대에 — 그러면 PM만이 할 수 있는 일은 뭘까요?"

**PM의 4가지 고유 역량:**

| # | 역량 | 설명 |
|---|------|------|
| 1 | **도메인 이해** | 실제 산업 현장의 맥락을 파악하고, 현재 상태에서 유의미한 방향성을 정의 |
| 2 | **비즈니스 판단** | 수익성, 신규 고객 유치 확장력, 대표/이사회/투자자 니즈를 종합 판단 |
| 3 | **제약 조건 내 최적화** | 주어진 예산·기간·개발 인력 안에서 가장 현실 가능하고 성과가 높은 제품 정의 |
| 4 | **기능 수준의 우선순위** | 기능 하나하나에 P0/P1/P2를 매기고, 무엇을 먼저 만들지 결정 |

> "AI는 정보를 수집하고 구조화하는 데 탁월합니다. 하지만 '이 회사의 상황에서, 지금 이걸 해야 하는가?'를 판단하는 건 PM의 몫입니다."

### [슬라이드 7] AI 시대, PM의 본질 = 맥락 설계자

**AI가 잘하는 것:**
- 시장 데이터 수집·분석
- 문서 구조화 (PRD 초안)
- 프로토타입 코드 생성
- 경쟁사 비교 정리

**PM만이 해야 하는 것:**
- "왜 지금 이것인가?" 판단
- 이해관계자 간 우선순위 조율
- 예산·일정·인력 제약 속 최적해
- Go/No-Go 의사결정

> "AI는 최고의 부사수입니다. 하지만 방향을 정하는 건 PM입니다. 오늘 배울 AI 도구들은 여러분의 판단력을 **증폭**시키는 도구입니다."

### [슬라이드 8] PM의 3가지 시대

| 시대 | 시기 | PM의 역할 | 핵심 도구 | 속도 |
|------|------|----------|----------|------|
| **Era 1: Feature PM** | ~2019 | 기능 정의자 | Jira, Word, PPT | 분기 단위 |
| **Era 2: Product-Led PM** | 2020~2024 | 성장 설계자 | Notion, Figma, A/B 테스트 | 2주 스프린트 |
| **Era 3: AI Native PM** | 2025~ | 의도 설계자 (Intent Architect) | Claude, Cursor, Manyfast | 시간~일 단위 |

### Era 1: Feature PM

> "PM이 Jira 티켓을 쓰고, 기획서를 Word로 작성하고, 개발팀에 전달하면 몇 주 후에 결과물이 나왔던 시대. 문서 → 전달 → 대기 → 확인의 선형적 흐름."

- 키워드: Waterfall, PRD as 문서, 전달자 역할
- 한계: 피드백 루프가 느리고, 만들어봐야 알 수 있는 것들이 너무 많았음

### Era 2: Product-Led PM

> "데이터 기반 의사결정, 린 스타트업, 그로스 해킹이 부상하면서 PM은 '실험 설계자'가 됐습니다. A/B 테스트를 설계하고, 퍼널을 분석하고, 지표를 추적하는 것이 핵심 역량이 됐죠."

- 키워드: 지표 중심, 스프린트, Figma 프로토타입
- 진전: 속도가 빨라졌지만, 여전히 디자이너/엔지니어에게 "부탁"해야 했음

### Era 3: AI Native PM

> "지금 우리가 진입한 시대입니다. PM이 직접 AI에게 의도를 전달하면, AI가 PRD를 구조화하고, 코드를 생성하고, 프로토타입을 만들어줍니다. **'Tell'에서 'Show'로** — 말로 설명하는 대신, 만들어서 보여주는 시대."

- Dennis Yang (Chime PM) 사례: PRD를 마크다운으로 작성 → Claude Code로 20분 만에 프로토타입 → 팀 미팅에서 실제 동작하는 결과물로 토론
- 핵심 변화: PM이 "문서 작성자"에서 **"맥락 설계자(Context Architect)"**로 진화
- **바이브 프로토타이핑 (Vibe Prototyping)**: 텍스트 프롬프트만으로 기능적 소프트웨어를 생성하는 새로운 접근 방식 (Forbes, 2026)

### [슬라이드 9] 무엇이 바뀌었나

| 구분 | Before | After |
|------|--------|-------|
| **문서** | Word → Notion → 수동 정리 | AI가 구조화된 PRD 초안 생성 |
| **프로토타입** | Sketch → Figma → 개발 의뢰 | AI가 PRD에서 바로 코드 생성 |
| **검증** | 기획서 리뷰 → 개발 → 출시 후 확인 (수 주) | 프로토타입으로 즉시 확인 (수 시간) |
| **역할** | PM: 전달자 / Dev: 구현자 | PM: 맥락 설계자 / AI: 실행 파트너 |

## Section 3: 기획 문서의 진화 (10분)

> **슬라이드 10~13 / 18:25~18:35**

### [슬라이드 10] 문서 계층 구조

```
2-Pager (왜 이걸 하는가? — 리더십 승인용)
  ↓ 승인되면
PRD (무엇을 만드는가? — 제품 요구사항 정의, SSOT)
  ├── Specs (어떻게 보이는가? — 와이어프레임, UX 흐름)
  ├── HLD/LLD (어떻게 구현하는가? — 기술 설계)
  └── ADR (왜 이렇게 결정했는가? — 의사결정 기록)
      ↓
Ops (어떻게 출시하는가? — 롤아웃 전략)
```

> "문서가 많아 보이지만, 핵심은 하나입니다. **PRD가 SSOT (Single Source of Truth)**이고, 나머지는 PRD의 특정 섹션을 더 깊이 파고드는 보조 문서입니다."

**용어 정리** (참가자 레벨에 맞춰):
- **PRD** (Product Requirements Document): 제품 요구사항 정의서
- **HLD** (High-Level Design): 상위 설계 — "어느 시스템에 어떻게 붙는가"
- **LLD** (Low-Level Design): 상세 설계 — "모듈과 API 수준 설계"
- **ADR** (Architecture Decision Record): 아키텍처 의사결정 기록 — "왜 이 선택을 했는가"

### [슬라이드 11] Why → What → How 프레임워크

> "좋은 PRD는 이 3가지 질문에 답합니다."

| 레벨 | 질문 | PRD에서 다루는 것 |
|------|------|-----------------|
| **Why** | 왜 이 문제를 풀어야 하는가? | 문제 정의, 비즈니스 근거, 데이터 증거 |
| **What** | 무엇을 만드는가? | 솔루션, 사용자, 범위, 시나리오, 기능 명세 |
| **How** | 어떻게 성공을 측정하는가? | 성공 지표, 실험 설계, 롤아웃 전략 |

> **"Why가 흔들리면 What과 How는 의미가 없습니다. 항상 Why부터."**

### [슬라이드 12] AI가 각 단계를 어떻게 바꾸는가

| 단계 | 전통 방식 | AI Native 방식 |
|------|----------|---------------|
| **2-Pager** | PM이 시장 조사 → 수일 소요 | AI에게 경쟁사/시장 데이터 분석 요청 → 수분 |
| **PRD** | PM이 템플릿에 수동 작성 → 1~2주 | 5개 핵심 입력 → AI가 구조화된 초안 생성 → 수시간 |
| **Wireframe** | 디자이너에게 의뢰 → 수일 대기 | AI 도구 (v0, Manyfast)가 PRD에서 UI 자동 생성 |
| **Prototype** | 엔지니어에게 의뢰 → 수주 대기 | Claude Code가 PRD에서 HTML 코드 즉시 생성 |

> "오늘 실습에서 여러분은 이 전체 흐름을 60분 안에 직접 경험합니다."

### [슬라이드 13] 5개 핵심 입력 — PRD의 씨앗

> "PRD 전체를 쓰지 않아도 됩니다. 이 5가지만 명확하면 AI가 나머지를 채워줍니다."

| # | 항목 | 질문 | 예시 (오늘의 점심 메이트) |
|---|------|------|------------------------|
| 1 | **서비스명** | 뭐라고 부를까? | 오늘의 점심 메이트 |
| 2 | **타겟 유저** | 누구를 위한 건가? | 점심 메뉴 고민이 많은 직장인 |
| 3 | **핵심 문제** | 어떤 문제를 해결하나? | 매일 "뭐 먹지?" 고민에 12분 낭비 |
| 4 | **AI 활용점** | AI가 어디서 가치를 만드나? | 기분/날씨/예산 기반 맞춤 메뉴 추천 |
| 5 | **성공 기준** | 어떻게 성공을 아나? | 추천 수락률 60% |

> "이 5개가 오늘 실습의 Step 1입니다. 미리 머릿속에 구상해두세요!"

## Section 4: 데모 — AI로 만든 서비스 (5분)

> **슬라이드 14~16 / 18:35~18:40**

### [슬라이드 14] 데모 1: PRD

> "이 5개 입력으로 만든 PRD를 보여드리겠습니다."

- **화면 공유**: `prd/PRD.md` 열기
- 하이라이트 포인트:
  - §3 문제 정의의 정량 데이터 (12분, 65%, 18분)
  - §4 AS-IS → TO-BE 비교표
  - §11 성공 지표 (KPI)와 Release Gate
  - §12 AI 모델 선택과 비용 추정 (월 $15)
- **핵심 멘트**: "5개 항목에서 시작해서, AI가 이 정도 수준의 PRD를 생성합니다. PM은 검증하고 보완하면 됩니다."

### [슬라이드 15] 데모 2: 프로토타입

> "이 PRD를 Claude Code에 넣으면 이런 결과물이 나옵니다."

- **화면 공유**: `demo-prototype.html` 브라우저에서 열기
- 라이브 시연:
  1. 기분 선택 (😊 기분 좋음)
  2. 예산 선택 (~1.5만원)
  3. AI 추천 결과 확인 (3개 메뉴 카드)
  4. "여기로 갈래요!" 클릭 → 수락 화면
- **핵심 멘트**: "이게 단일 HTML 파일입니다. Claude Code에 PRD 핵심 내용을 붙여넣고 15분 만에 만들었습니다."

### [슬라이드 16] 전환 — 이제 여러분 차례

> "지금까지 제가 보여드린 건 **아이디어 → PRD → 프로토타입** 흐름입니다. 잠시 쉬고 돌아오면, 여러분이 직접 이 과정을 체험합니다."

- 실습 안내:
  - 19:10 쉬는 시간 (10분, 노트북 세팅 최종 확인)
  - 19:20 실습 시작 (60분)
- **하나만 기억하세요**: 완성도가 아니라 **과정을 체험하는 것**이 목적입니다.
