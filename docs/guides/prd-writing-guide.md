## 1. PRD란 무엇인가

### 정의

**PRD (Product Requirements Document, 제품 요구사항 정의서)** 는 "왜 이 제품을 만드는가, 무엇을 만드는가, 어떻게 성공을 측정하는가"를 하나의 문서에 담은 것이다.

PRD는 제품 개발의 **SSOT (Single Source of Truth, 단일 진실 원본)** 역할을 한다. 프로젝트에 참여하는 모든 사람 — PM, 디자이너, 개발자, QA, 리더십 — 이 "우리가 뭘 만들고 있지?"라는 질문에 같은 답을 할 수 있게 해주는 문서다.

### PRD가 아닌 것

| 흔한 오해 | 실제 |
|-----------|------|
| "와이어프레임이 있으면 PRD 아닌가요?" | PRD는 와이어프레임의 **근거**를 제공한다. 디자이너가 PRD를 읽고 와이어프레임을 그린다 |
| "기능 목록이 PRD 아닌가요?" | 기능 목록은 PRD의 일부(Functional Spec)일 뿐이다. "왜"와 "성공 기준"이 없으면 PRD가 아니다 |
| "기술 설계서가 PRD 아닌가요?" | 기술 설계는 HLD/LLD 문서의 역할이다. PRD는 "무엇을"에 집중하고, "어떻게 구현하는가"는 엔지니어가 판단한다 |
| "길면 좋은 PRD인가요?" | 아니다. 좋은 PRD는 **필요한 만큼만** 쓴다. 불필요한 섹션은 과감히 생략하되, 필수 섹션은 반드시 채운다 |

### PRD의 독자

PRD는 하나의 문서가 여러 독자에게 다른 가치를 제공한다:

| 독자 | PRD에서 찾는 것 |
|------|---------------|
| **리더십/임원** | 왜 이 프로젝트에 투자해야 하는가? ROI (Return on Investment, 투자 대비 수익률)는? |
| **디자이너** | 어떤 시나리오를 디자인해야 하는가? 가드레일(Guardrail, 안전 장치)과 예외 상황은? |
| **개발자** | 기능 요구사항은 무엇이고, 성능 기준은? 범위(Scope)의 경계는 어디까지? |
| **QA** | 무엇을 테스트해야 하는가? 성공/실패의 기준은? |
| **데이터 분석가** | 어떤 지표를 추적해야 하는가? 이벤트 설계는? |

## 2. Why → What → How 프레임워크

좋은 PRD는 세 가지 질문에 순서대로 답한다. **하나라도 빠지면 PRD가 아니라 메모**에 불과하다.

```
┌─────────────────────────────────────────┐
│  Why (왜 만드는가)                        │
│  → 문제 정의, 비즈니스 맥락, 고객 고통점      │
│                                         │
│  ┌─────────────────────────────────┐    │
│  │  What (무엇을 만드는가)            │    │
│  │  → 솔루션, 범위, 페르소나, 시나리오    │    │
│  │                                 │    │
│  │  ┌─────────────────────────┐    │    │
│  │  │  How (어떻게 검증하는가)    │    │    │
│  │  │  → KPI, 실험, 출시 전략    │    │    │
│  │  └─────────────────────────┘    │    │
│  └─────────────────────────────────┘    │
└─────────────────────────────────────────┘
```

### Why — 왜 만드는가

| 답해야 할 질문 | PRD 섹션 |
|---------------|----------|
| 사용자가 겪고 있는 고통은 무엇인가? | §3 Problem Definition (문제 정의) |
| 이 문제를 풀어야 하는 비즈니스 근거는? | §2 Executive Summary (요약) |
| 왜 **지금** 해야 하는가? | §1 Project Header (프로젝트 개요) |
| 데이터로 뒷받침되는 근거가 있는가? | §3 Problem Definition |

**없으면 생기는 문제**: "왜 이걸 만드는지 모르겠다"는 리더십 피드백. 우선순위 논쟁이 끝나지 않음.

### What — 무엇을 만드는가

| 답해야 할 질문 | PRD 섹션 |
|---------------|----------|
| 핵심 솔루션은 무엇인가? | §4 Solution Proposed (솔루션 제안) |
| 누구를 위한 것인가? | §5 Target Persona (대상 사용자) |
| 이번 릴리즈의 범위는? 안 하는 것은? | §6 Scope (범위) |
| 사용자의 핵심 시나리오는? | §7 Core Scenarios (핵심 시나리오) |
| 화면 구성과 진입점은? | §8 Entry Surface & UX |
| 기능별 요구사항은? | §9 Functional Spec (기능 명세) |

**없으면 생기는 문제**: 디자이너가 "이 화면에서 뭘 보여줘야 하는지 모르겠다"고 되묻기. 개발자가 범위를 자의적으로 해석.

### How — 어떻게 검증하는가

| 답해야 할 질문 | PRD 섹션 |
|---------------|----------|
| 성공을 어떻게 측정하는가? | §11 Success Metrics / KPI |
| 성능·안정성 기준은? | §10 Non-Functional Requirements (비기능 요구사항) |
| 단계적 출시 계획은? | §16 Rollout Strategy (출시 전략) |
| 일정과 담당자는? | §17 Milestones, §18 Team Ownership |
| 실험 설계는? | §14 Experiment Design |

**없으면 생기는 문제**: 출시 후 "성공인지 실패인지 판단할 수 없음". 릴리즈 게이트 없이 무분별한 출시.

## 3. 섹션별 상세 가이드

### §0. 메타 헤더 & Change Log (필수)

**목적**: 문서의 상태, 이력, 소유자를 추적한다.

CLAUDE.md의 Document Authoring Standards를 따른다. 모든 PRD의 최상단에 메타 헤더를 배치하고, 바로 아래에 접이식 Change Log를 둔다.

> **이 섹션이 없으면**: 문서의 최신 버전이 뭔지, 누가 마지막으로 수정했는지 알 수 없다.

---

### §1. Project Header (프로젝트 개요) (필수)

**목적**: 프로젝트의 맥락을 30초 안에 파악할 수 있게 한다.

**포함 내용**:

| 항목 | 설명 |
|------|------|
| 2-Pager 링크 | 의사결정용 요약 문서 |
| Jira Epic / 티켓 | 개발 추적 링크 |
| 출시 목표 일자 | YYYY-MM-DD |
| 팀 구성 | PM, Design, Backend, Frontend, QA 각 담당자 |
| 관련 문서 링크 | HLD, 와이어프레임, 브랜딩 가이드 등 |

**좋은 예**:
```
| 항목 | 내용 |
|------|------|
| 2-Pager | [검색 랭킹 개선 2-Pager](../2pager.md) |
| Epic | SEARCH-1234 |
| 출시 목표 | 2026-06-30 (Q3 초) |
| PM | 홍길동 |
| Design | 김디자 |
| Backend | 박백엔 |
```

**나쁜 예**: 팀 구성 없이 PM 이름만 적거나, 출시 목표 일자가 없는 경우.

> **이 섹션이 없으면**: "이 프로젝트 언제까지야?", "담당 개발자 누구야?" 같은 기본 질문에 답할 수 없다.

---

### §2. Executive Summary (요약) (필수)

**목적**: 리더십이 5문장 이내로 프로젝트를 이해할 수 있게 한다.

**포함 내용**: 문제 한 줄, 솔루션 한 줄, 대상 사용자 한 줄, 핵심 지표 한 줄, 일정 한 줄

**좋은 예**:
> 무신사 앱 내 검색 결과의 62%가 사용자 의도와 불일치하며(문제), AI 기반 검색 랭킹 모델을 도입하여(솔루션) 월 100만 이상 검색하는 액티브 쇼퍼를 대상으로(사용자) CTR (Click-Through Rate, 클릭률)을 현재 3.2%에서 5.0%로 개선한다(지표). Q3 초 출시 목표(일정).

**나쁜 예**:
> 검색을 개선합니다. AI를 활용할 예정입니다. → *"무엇이 문제이고, 얼마나 개선되는지"가 없다*

> **이 섹션이 없으면**: 리더십이 PRD 전체를 읽어야 프로젝트를 판단할 수 있다. 현실적으로 읽지 않게 된다.

---

### §3. Problem Definition (문제 정의) (필수)

**목적**: "왜 이 문제를 풀어야 하는가"를 **데이터와 근거**로 설명한다.

**포함 내용**:

| 항목 | 설명 |
|------|------|
| 사용자 고통점 (Pain Point) | 구체적 행동 패턴 + 정량 데이터 |
| 비즈니스 영향 | 매출·비용·이탈률 등 수치화된 영향 |
| 근거 자료 | VOC (Voice of Customer, 고객 의견), 사용자 리서치, 로그 분석 |
| 현재 상태 (AS-IS) | 지금은 어떻게 하고 있는가 |

**좋은 예**:
> P1. 검색 결과 불일치: 사용자 설문(N=500) 결과, "원하는 상품을 찾기 어렵다" 응답 62.2%. 검색 후 이탈률 45%, 재검색 비율 38%.

**나쁜 예**:
> 검색이 별로다. 사용자들이 불편해한다. → *정량 데이터와 구체적 근거가 없다*

> **이 섹션이 없으면**: "이거 정말 문제인가요?"라는 근본적 질문에 답할 수 없다. 솔루션이 "해결책을 찾는 문제"가 된다.

**AI가 잘하는 부분**: 경쟁사 분석 초안, 시장 데이터 정리, 유사 사례 벤치마킹
**PM이 직접 써야 하는 부분**: 우선순위 판단 (P1 vs P2), 자사 데이터 해석, Trade-off (상충 관계) 결정

---

### §4. Solution Proposed (솔루션 제안) (필수)

**목적**: 문제를 어떻게 풀 것인지 **가설 기반으로** 제안한다.

**포함 내용**:

| 항목 | 설명 |
|------|------|
| 핵심 가설 | "만약 X를 하면, Y가 될 것이다" |
| AS-IS → TO-BE | 현재 상태에서 목표 상태로의 변화 |
| 핵심 접근 방식 | 기술적 방향 (개략적 수준) |
| 분기별 방향 | Q2/Q3/Q4+ 단계적 진화 방향 (해당 시) |

**핵심 원칙**: 솔루션은 **가설**이다. "이렇게 하면 될 것이다"가 아니라 "이렇게 하면 될 것이라고 **예상**한다. 검증 방법은 §11 KPI와 §14 실험 설계에서 정의한다."

> **이 섹션이 없으면**: 개발팀이 "그래서 뭘 만들라는 건가요?"라고 묻게 된다.

---

### §5. Target Persona (대상 사용자) (필수)

**목적**: "누구를 위해 만드는가"를 명확히 한다.

**포함 내용**:

| 우선순위 | 페르소나 | 특성 | 핵심 니즈 |
|----------|---------|------|----------|
| P0 (최우선) | [이름/유형] | [행동 패턴, 빈도] | [해결하고자 하는 것] |
| P1 (중요) | [이름/유형] | [행동 패턴, 빈도] | [해결하고자 하는 것] |
| P2 (향후) | [이름/유형] | [행동 패턴, 빈도] | [해결하고자 하는 것] |

**좋은 예**:
> P0 — 탐색형 쇼퍼: 월 10회 이상 검색, 검색어 평균 2.5단어, 카테고리 필터 미사용, "좋은 거 추천해줘" 유형

**나쁜 예**:
> 20대 여성 → *너무 넓다. 행동 패턴과 니즈가 없다*

---

### §6. Scope (범위) (필수)

**목적**: "이번에 하는 것"과 "안 하는 것"의 경계를 명확히 한다.

세 가지로 나눈다:

| 분류 | 의미 |
|------|------|
| **In Scope (범위 내)** | 이번 릴리즈에 반드시 포함 |
| **Out of Scope (범위 외)** | 의도적으로 이번에 하지 않는 것 |
| **Future Consideration (향후 고려)** | 다음 분기 이후 검토 대상 |

**핵심 원칙**: Out of Scope가 없는 PRD는 범위가 불명확한 PRD다. "안 하는 것"을 명시적으로 적어야 범위 합의가 된다.

> **이 섹션이 없으면**: 개발 중간에 "이것도 해야 하지 않나요?"라는 Scope Creep (범위 확장)이 발생한다.

---

### §7. Core Scenarios (핵심 시나리오) (조건부 필수)

**트리거 조건**: AI 제품, Agent 기반, 대화형 UX, 복잡한 사용자 플로우가 있는 프로젝트

**목적**: 사용자의 핵심 사용 흐름을 시나리오로 정의한다.

**포함 내용**:

| 항목 | 설명 |
|------|------|
| 시나리오 ID | SC-01, SC-02, ... |
| 사용자 의도 | "무엇을 하려고 하는가" |
| 트리거 (시작점) | 어떤 행동으로 시작되는가 |
| 주요 단계 | 사용자 액션 → 시스템 응답 흐름 |
| 예상 결과 | 시나리오 성공 시 사용자가 보는 것 |
| 우선순위 | P0 / P1 |
| 연관 화면 | IMG-XX 참조 |

**좋은 예**:
> SC-01. 탐색 시작형: 사용자가 "봄에 입기 좋은 자켓" 입력 → 시스템이 3개 카테고리 추천 + 필터 칩 제시 → 사용자가 칩 선택하여 결과 좁힘 → 상품 상세 진입

> **이 섹션이 없으면**: 디자이너가 "사용자가 어떤 순서로 행동하는지"를 추측해서 디자인한다. QA가 무엇을 테스트해야 하는지 모른다.

---

### §8. Entry Surface & UX (진입 지면·UX) (조건부 필수)

**트리거 조건**: 대고객 서비스, 신규 UX 도입, 여러 진입점이 있는 프로젝트

**목적**: 사용자가 이 기능에 **어디서, 어떻게** 접근하는지를 정의한다.

**포함 내용**:

| 항목 | 설명 |
|------|------|
| 진입점 (Entry Point) | 어떤 화면에서 이 기능에 접근하는가 |
| 노출 조건 | 어떤 조건에서 보이는가 (타겟팅, A/B 테스트) |
| 화면 전환 흐름 | 진입 → 인터랙션 → 결과 → 이탈 |
| 출력 원칙 | 메시지 포맷, 컴포넌트 유형, 디자인 토큰 |
| 핵심 정책 | 세션 정책, 최대 노출 빈도 등 |

> **이 섹션이 없으면**: 디자이너가 진입점과 화면 전환을 자의적으로 설계한다.

---

### §9. Functional Spec (기능 명세) (필수)

**목적**: 구현해야 할 기능을 **요구사항 테이블**로 정리한다.

**권장 포맷**:

| ID | 기능명 | 화면 | 우선순위 | 기대 결과 | 비고 |
|----|-------|------|---------|----------|------|
| F-01 | 검색어 자동완성 | 검색 화면 | P0 | 입력 2글자부터 자동완성 후보 5개 표시 | 최대 응답 시간 200ms |
| F-02 | AI 추천 카드 | 검색 결과 | P1 | 검색 결과 상단에 AI 추천 이유 표시 | A/B 테스트 대상 |

**핵심 원칙**: 기능 명세는 "무엇을 해야 하는가"를 쓰는 것이지, "어떻게 구현하는가"를 쓰는 것이 아니다. 구현 방법은 엔지니어가 HLD/LLD에서 결정한다.

> **이 섹션이 없으면**: "그래서 정확히 뭘 만들어야 하는 건가요?"라는 개발자의 질문이 반복된다.

---

### §10. Non-Functional Requirements (비기능 요구사항) (조건부 필수)

**트리거 조건**: API/플랫폼, 대규모 트래픽, 결제·보안 연관 프로젝트

**목적**: 성능, 안정성, 보안 등 "기능 외의 품질 기준"을 정의한다.

**포함 내용**:

| 항목 | 기준 | 측정 방법 |
|------|------|----------|
| 응답 시간 (Latency) | p50 < 1s, p95 < 3s | APM (Application Performance Monitoring) 대시보드 |
| 가용성 (Availability) | 99.9% | 모니터링 시스템 |
| 동시 접속 (Concurrency) | 1,000 TPS | 부하 테스트 |
| 보안 | OWASP Top 10 준수 | 보안 감사 |

---

### §11. Success Metrics / KPI (성공 지표) (필수)

**목적**: "이 프로젝트가 성공했는지 어떻게 판단하는가"를 정의한다.

**3단계 지표 계층**:

| 계층 | 역할 | 예시 |
|------|------|------|
| **NSM (North Star Metric, 핵심 목표 지표)** | 장기적으로 추적하는 단일 지표 | 검색 후 구매 전환율 |
| **핵심 성공 지표 (Primary Success)** | 이번 분기에 직접 움직이려는 지표 (3-5개) | CTR, 재검색률, 세션 깊이 |
| **보조 지표 (Supporting)** | 핵심 지표의 선행·후행 지표 | 검색 응답 시간, 무결과 비율 |

**좋은 예**:
> NSM: 검색-구매 전환율 (현재 2.1% → 목표 3.0%)
> 핵심 성공 지표: CTR 3.2% → 5.0%, 재검색률 38% → 25%, 평균 세션 깊이 2.3 → 3.5

**나쁜 예**:
> 사용자 만족도 향상 → *측정 방법과 목표 수치가 없다*

> **이 섹션이 없으면**: 출시 후 "성공인가 실패인가?"를 판단할 수 없다.

**AI가 잘하는 부분**: 벤치마크 지표 조사, KPI 프레임워크 초안 작성
**PM이 직접 써야 하는 부분**: 목표 수치 설정, 측정 가능성 검증, 팀 합의

---

### §12. AI Model & Technical Assumptions (AI 모델·기술 전제) (조건부 필수)

**트리거 조건**: AI/ML (Machine Learning, 기계 학습) 제품

**목적**: 어떤 AI 모델을 쓰고, 기술적 전제 조건은 무엇인지 명시한다.

**포함 내용**: 기본 모델, 품질 모델, 제외 모델 및 이유, 프롬프트 전략 방향, 예상 비용

---

### §13. Policy & Guardrails (정책·가드레일) (조건부 필수)

**트리거 조건**: 대고객 서비스, 결제·정산 연관, 개인정보 처리

**목적**: 서비스 정책, 예외 처리, 안전 장치를 정의한다.

**포함 내용**:

| 항목 | 설명 |
|------|------|
| 허용 범위 | 시스템이 처리할 수 있는 입력 범위 |
| 금지 행위 | 시스템이 절대 하면 안 되는 것 |
| 폴백 시나리오 (Fallback) | 오류·예외 시 대안 동작 |
| 개인정보 처리 | PII (Personally Identifiable Information, 개인 식별 정보) 처리 규칙 |
| 컴플라이언스 (Compliance) | 법적·규제 준수 사항 |

> **이 섹션이 없으면**: 서비스 장애 시 "어떻게 대응해야 하지?"라는 혼란이 발생한다.

---

### §14. Experiment Design (실험 설계) (조건부 필수)

**트리거 조건**: A/B 테스트 기반 개발

**목적**: 가설 검증을 위한 실험 구조를 정의한다.

**포함 내용**: 실험 가설, 대조군/실험군 정의, MDE (Minimum Detectable Effect, 최소 감지 효과), 예상 소요 기간, 의사결정 기준

---

### §15. Event Logging (이벤트 로깅) (조건부 필수)

**트리거 조건**: 데이터 분석이 필수인 프로젝트

**목적**: 추적해야 할 사용자 이벤트의 분류(Taxonomy)를 정의한다.

**포함 내용**: 이벤트명, 발생 조건, 파라미터, 지면(Surface)

---

### §16. Rollout Strategy (출시 전략) (조건부 필수)

**트리거 조건**: 점진적 오픈이 필요한 프로젝트

**목적**: 단계별 출시 계획과 각 단계의 진입/퇴출 기준을 정의한다.

**포함 내용**:

| 단계 | 트래픽 | 기간 | 진입 기준 | 퇴출(롤백) 기준 |
|------|--------|------|----------|---------------|
| 내부 테스트 | 0% (사내) | 1주 | QA 완료 | 크리티컬 버그 0건 |
| Limited Open | 1-5% | 2주 | 내부 테스트 통과 | 에러율 > 1% |
| Gradual Rollout | 5% → 50% | 4주 | KPI 달성 | 핵심 지표 하락 |
| Full Release | 100% | - | 전 단계 통과 | - |

---

### §17. Milestones & Schedule (일정·마일스톤) (필수)

**목적**: 주요 일정과 각 마일스톤의 산출물을 정의한다.

**포함 내용**: 마일스톤명, 목표 일자, 산출물, 담당자, 의존성

---

### §18. Team Ownership (팀 구성·역할) (필수)

**목적**: 역할별 담당자와 R&R (Role & Responsibility, 역할 및 책임)을 명시한다.

| 역할 | 담당자 | 책임 |
|------|--------|------|
| PM | 홍길동 | PRD 작성·유지, 우선순위 관리, 일정 조율 |
| Design | 김디자 | 와이어프레임, 프로토타입, UI 명세 |
| Backend | 박백엔 | API 설계·구현, 데이터 모델 |
| Frontend | 이프론 | UI 구현, 인터랙션 |
| QA | 최큐에이 | TC 작성, 테스트 실행, 릴리즈 게이트 검증 |

---

### §19. Appendix (부록) (옵션)

**목적**: 본문에 넣기엔 길지만 참고해야 하는 자료를 모은다.

경쟁사 분석, 사용자 리서치 원본, 기술 벤치마크, 관련 ADR 링크 등.

---

### §20. Experiment Results (실험 결과) (옵션)

**목적**: A/B 테스트 완료 후 결과를 기록한다. 출시 전에는 비어 있는 것이 정상이다.

## 5. PRD 작성 Best Practices

### 원칙 1: 두괄식 작성 (결론 먼저)

각 섹션의 첫 문장에 핵심 메시지를 넣는다. 리더십은 첫 줄만 읽을 수 있다.

```
❌ "다양한 분석을 수행한 결과... (3문단 후) ...결론적으로 CTR이 낮습니다."
✅ "검색 결과 CTR이 3.2%로 업계 평균(6.5%) 대비 절반 수준이다. 주요 원인은..."
```

### 원칙 2: Link > Duplicate (복사 금지)

다른 문서의 내용을 복사하지 않는다. 링크로 참조한다.

```
❌ (HLD 내용을 PRD에 그대로 복사)
✅ "기술 아키텍처는 [HLD](../decisions/hld/HLD.md) 참조"
```

### 원칙 3: 구체적 > 추상적

형용사 대신 숫자를 쓴다.

```
❌ "빠른 응답 속도를 목표로 한다"
✅ "응답 시간 p95 < 3초를 목표로 한다"
```

### 원칙 4: MECE (Mutually Exclusive, Collectively Exhaustive) Scope

범위 정의 시 누락도 중복도 없어야 한다. 특히 Out of Scope를 명시적으로 적는다.

```
❌ In Scope만 나열
✅ In Scope + Out of Scope + Future Consideration 3가지 모두 작성
```

### 원칙 5: 가설 기반 솔루션

솔루션은 확정이 아니라 가설이다. "하면 된다"가 아니라 "하면 될 것으로 예상하며, 이렇게 검증한다"로 쓴다.

```
❌ "AI 랭킹 모델을 적용하면 CTR이 올라간다"
✅ "AI 랭킹 모델을 적용하면 CTR이 5%로 개선될 것으로 가설을 세운다. 
    A/B 테스트로 2주간 검증하며, MDE 1.5%p 기준으로 판단한다"
```

## 6. AI를 활용한 PRD 작성 팁

### 핵심 원칙: 프롬프트 품질 = PRD 품질

Claude에게 좋은 PRD를 받으려면, 좋은 입력을 제공해야 한다. "PRD 써줘"는 좋은 프롬프트가 아니다.

### AI가 잘하는 것 vs PM이 직접 해야 하는 것

| AI가 잘하는 것 | PM이 직접 해야 하는 것 |
|--------------|---------------------|
| 경쟁사 분석 초안 작성 | 우선순위 판단 (P0/P1/P2) |
| 시장 데이터 정리·요약 | 자사 데이터 해석·인사이트 도출 |
| KPI 프레임워크 초안 | 목표 수치 설정 (현실성 판단) |
| 기능 명세 테이블 초안 | Trade-off 결정 (기능 A vs B) |
| 리스크 목록 초안 | 이해관계자 합의·조율 |
| 문서 구조화·포맷팅 | 전략적 판단·의사결정 |
| 누락 섹션 점검 | 비즈니스 맥락 제공 |

### Draft-Review 패턴 (추천 워크플로우)

```
1. PM이 컨텍스트 준비    → docs/references/prd-generation-prerequisites.md 체크리스트 확인
2. AI가 PRD 초안 생성    → "이 컨텍스트로 PRD를 작성해줘" (입력물과 함께)
3. PM이 리뷰·보완        → 숫자 검증, 우선순위 조정, 전략적 판단 보강
4. AI 평가 프롬프트 실행  → docs/evaluation/ 의 3관점 평가로 자가 점검
5. PM이 미달 항목 보완    → 점수 낮은 항목 집중 보완
6. 이해관계자 리뷰 요청   → Status를 "In Review"로 변경
```

### AI에게 좋은 입력을 주는 방법

**필수 제공 정보**:
- 비즈니스 목표 / OKR (Objectives and Key Results, 목표 및 핵심 결과)
- 해결할 사용자 문제 (구체적 Pain Point)
- 자사 데이터 (관련 지표 현황)
- 제약 조건 (일정, 예산, 기술, 정책)

**선택 제공 정보**:
- 사용자 리서치 결과
- 경쟁사 분석
- 기존 관련 문서 (이전 분기 PRD, ADR 등)
- 조직도·담당자 정보

> 더 자세한 체크리스트는 [PRD 생성 준비물 가이드](../references/prd-generation-prerequisites.md)를 참조한다.
